# DDD-модель предметной области

Источники: [wallet_business_prompt_ru_v2.md](../requirements/wallet_business_prompt_ru_v2.md), [user-scenarios.md](../requirements/user-scenarios.md), [glossary.md](../requirements/glossary.md), ADR-0001…ADR-0006.

Технические идентификаторы (названия контекстов, агрегатов, сущностей, VO) — на английском, пояснения — на русском, как того требует CLAUDE.md.

## Общие соглашения

- **Строго типизированные идентификаторы.** Каждый агрегат имеет собственный ID-тип (`WalletId`, `OperationId`, `TransferId`, `BalanceSnapshotId`, `WalletTypeId`, `OperationTypeId`, `AuditEntryId`) — обертка над `Guid`, чтобы исключить путаницу идентификаторов разных сущностей на уровне типов.
- **Мутация только через корень агрегата.** Внешний код не изменяет внутренние поля агрегата напрямую — только через методы агрегата, которые поддерживают инварианты и порождают доменные события.
- **Модульный монолит = границы bounded context.** Каждый bounded context ниже соответствует отдельному модулю в решении (см. этап «Высокоуровневая архитектура»); модули общаются между собой только через доменные события и явные контракты (интерфейсы), не через прямые ссылки на внутренние типы друг друга.
- **Audit — сквозной (cross-cutting) контекст.** Он ничего не решает о бизнес-правилах, а подписывается на доменные события всех остальных контекстов и пишет неизменяемый журнал.

## 1. Ограниченные контексты (Bounded Contexts)

| Контекст | Назначение | Владеет агрегатами |
|---|---|---|
| **Wallets** | Управление кошельками, единственный основной кошелек, текущий (проекционный) баланс | `Wallet` |
| **ReferenceData** | Расширяемые справочники: типы кошельков, типы операций, валюты (активные) и список доступных валют сервиса курсов; плюс системный (не редактируемый пользователем) справочник видов поведения операции | `WalletType`, `OperationType`, `Currency`, `AvailableCurrency`, `OperationBehaviorKind` |
| **Operations** | Операции (доход/расход/корректировка) и переводы между кошельками | `Operation`, `Transfer` |
| **BalanceHistory** | Ежедневные слепки истории баланса, каскадный пересчет | `BalanceSnapshot` |
| **ExchangeRates** | Курсы валют от Frankfurter, кэш последнего успешного курса, загружаемая история курсов на дату и учет покрытия этой истории; загрузка списка доступных валют | `ExchangeRateQuote` (+ служебная сущность `HistoricalRateCoverage`) |
| **Audit** | Неизменяемый журнал изменений финансовых данных (сквозной, подписчик событий) | `AuditEntry` |
| **Reporting** *(read-only, без агрегатов)* | Расчет общей суммы и исторической общей суммы — композиция данных Wallets + BalanceHistory + ExchangeRates. Не хранит собственное состояние, не порождает событий, только запросы (query-side). | — |

### Карта контекста (Context Map)

```
ReferenceData ←────────── Wallets           (Wallet ссылается на WalletType и Currency по Id)
ReferenceData ←────────── Operations         (Operation ссылается на OperationType по Id; OperationType ссылается на OperationBehaviorKind по Id)
ReferenceData ←────────── ExchangeRates      (ExchangeRateQuote ссылается на пару Currency по Id)
Wallets       ←────────── Operations         (Operation ссылается на WalletId; событие меняет CurrentBalance кошелька)
Operations    ──событие──▶ BalanceHistory    (изменение операции триггерит пересчет слепков, см. ADR-0003)
Operations    ──событие──▶ BalanceHistory    (также восстановление операции/перевода: OperationRestored, см. ADR-0002, ADR-0003)
Wallets       ──событие──▶ BalanceHistory    (WalletDeleted — удалить слепки кошелька; WalletCurrencyChanged — перестроить слепки в новой валюте, ADR-0002 §2)
ReferenceData ──событие──▶ ExchangeRates     (CurrencyDeleted — удалить курсы и покрытие истории удаленной валюты, ADR-0002 §4; CurrencyCreated — догрузить курс и историю новой активной валюты, ADR-0004 §9)
Wallets       ──событие──▶ ExchangeRates     (WalletCreated, WalletCurrencyChanged, PrimaryWalletChanged — догнать курсы и историю до нужного состояния, ADR-0004 §5, §9)
ExchangeRates ──запись──▶ ReferenceData      (список доступных валют, загруженный из сервиса, передается ReferenceData на сохранение; ADR-0004 §7)
Wallets       ──запись──▶ ReferenceData      (создание кошелька: выбранная валюта гарантированно активна — активируется из доступных в той же транзакции; ADR-0004 §7)
BalanceHistory ──запрос──▶ Operations        (суммы не удаленных операций кошелька для расчета слепков, ADR-0003 §1)
Wallets       ──запрос──▶ Operations         (hasHistory: есть ли у кошелька операции, включая мягко удаленные, ADR-0002 §2)
ReferenceData ──запрос──▶ Wallets, Operations (isUsed: используется ли элемент справочника кошельками и операциями, включая мягко удаленные, ADR-0002 §4)
Wallets, BalanceHistory, ExchangeRates ──запрос──▶ Reporting  (композиция для Total Amount / Historical Total Amount)
Wallets, ReferenceData, Operations, BalanceHistory, ExchangeRates ──событие──▶ Audit  (подписка на все события, запись журнала)
```

Все связи между Wallets, ReferenceData, Operations и BalanceHistory — это связи только по идентификатору (Id) плюс доменные события; ни один контекст не хранит и не модифицирует данные другого контекста напрямую.

## 2. Агрегаты и их границы

### 2.1 Wallet (контекст Wallets)

Агрегат из одной сущности `Wallet` (корень = сама сущность). Инкапсулирует все атрибуты кошелька из раздела 1 требований плюс `CurrentBalance` — кэшированное значение, синхронизируемое обработчиком событий из контекста Operations в той же транзакции, что и создание/изменение/мягкое удаление/восстановление операции (мягко удаленные операции в `CurrentBalance` не учитываются).

**Граница агрегата:** ровно один кошелек. `CurrentBalance` — часть агрегата (не отдельный агрегат), так как должна быть согласована с атрибутами кошелька мгновенно (нет «текущего баланса без кошелька»). История операций и слепков **не входит** в агрегат — это отдельные агрегаты в других контекстах, иначе агрегат Wallet рос бы неограниченно и стал бы узким местом для конкурентного доступа.

Инвариант «ровно один основной кошелек» — это **инвариант на уровне всей коллекции агрегатов** (не одного агрегата), поэтому он не может быть обеспечен только логикой одного `Wallet`; он реализуется на уровне доменного сервиса (`PrimaryWalletPolicy`), выполняющегося в той же транзакции при назначении нового основного кошелька (снимает флаг со старого, ставит на новый).

### 2.2 WalletType, OperationType, Currency (контекст ReferenceData) — пользовательские справочники

Три независимых агрегата из одной сущности каждый. `WalletType` и `OperationType` — простые справочные записи с жизненным циклом создание → (использование) → деактивация, либо создание → удаление (если не использован — см. ADR-0002). Пользователь может свободно добавлять новые элементы (раздел 7 требований). У `Currency` третьего состояния нет: запись либо существует (валюта **активна**), либо удалена (см. ниже).

`Currency` (решено при проектировании домена, см. раздел «Решения, принятые при формализации домена» в конце документа; изменено [ADR-0004](./adr/0004-currencies-and-exchange-rates.md), §7) хранит код валюты и название. **Признака активности у нее нет:** запись `Currency` — это и есть активная валюта пользователя; «добавить в активные» — создать запись (`CurrencyCreated`), «убрать из активных» — удалить ее (`CurrencyDeleted`), если она не используется. Название — английское, из сервиса; при обновлении списка доступных валют название активной валюты приводится к названию сервиса (`Rename`, событие `CurrencyRenamed`, только если название изменилось). Это справочник по той же схеме, что `WalletType`/`OperationType`, а не просто валидированная строка, но **набор допустимых кодов задает не пользователь, а список доступных валют** — см. `AvailableCurrency`.

**`AvailableCurrency`** (ReferenceData) — запись списка доступных валют: код (первичный ключ), английское название, момент последнего обновления. Агрегат из одной сущности **без доменных событий** и без пользовательских команд: список заменяется целиком по данным сервиса курсов (`ReplaceAvailableCurrencies`, вызывается из ExchangeRates через порт ReferenceData), пользователь им не управляет. Нужен только для списков выбора и для проверки «код есть среди доступных» при добавлении валюты в активные и при создании кошелька. Не связан с `Currency` внешним ключом: валюта, которую сервис убрал из списка, остается активной (ADR-0004 §6); существующие валюты, которых в сервисе нет, тоже остаются активными (выведено при реализации).

**Граница агрегата:** один элемент справочника. Проверка «используется ли элемент существующими записями» (блокирующая физическое удаление) выполняется доменным сервисом на уровне приложения, а не самим агрегатом — агрегат `WalletType`/`OperationType`/`Currency` не может и не должен знать о существовании `Wallet`/`Operation` из других контекстов. Использованием считаются только ссылки от `Wallet` (включая архивные) и `Operation` (включая мягко удаленные); записи `ExchangeRateQuote` использованием валюты не считаются (ADR-0002 §4).

### 2.3 OperationBehaviorKind (контекст ReferenceData) — системный справочник

Агрегат из одной сущности, представляющий фиксированный набор базовых видов поведения операции: `Income`, `Expense`, `Transfer`, `Adjustment` (раздел 3 требований). Технически это таблица-справочник, а не закрытый enum в коде (решено при проектировании домена — пользователь явно потребовал именно табличное представление), но **в отличие от `WalletType`/`OperationType`/`Currency` пользователь не может создавать, редактировать или деактивировать её элементы** — набор строк сеется один раз при развертывании и добавление нового значения требует обновления приложения (раздел 3: «добавление нового принципиально иного поведения операции может требовать обновления приложения»), так как каждое значение жестко связано с кодом, который умеет его интерпретировать (как оно влияет на баланс, нужно ли создавать вторую операцию и т.д.).

`OperationType` ссылается на `OperationBehaviorKind` по Id — это единственная связь, которая делает пользовательский элемент справочника `OperationType` («зарплата», «продукты», …) семантически осмысленным для остальной системы.

**Граница агрегата:** один элемент справочника поведения.

### 2.4 Operation (контекст Operations)

Агрегат из одной сущности `Operation`. Представляет единичную финансовую запись: доход, расход или корректировку. Не включает в себя данные кошелька (только `WalletId`) и не включает данные о переводе, кроме опциональной обратной ссылки `TransferId` (см. ниже).

**Граница агрегата:** одна операция. Все проверки, требующие данных о кошельке (совпадение валюты, статус архивирования) или о справочнике (активность типа операции), выполняются доменным сервисом уровня приложения на момент создания/редактирования, а не самим агрегатом.

**Жизненный цикл (ADR-0002 §3).** Операция несет `DeletedAt: DateTimeOffset?` (`null` — не удалена) и вычисляемый `IsDeleted`. Удаление — только мягкое: метод `SoftDelete()` заполняет `DeletedAt` и порождает `OperationDeleted`, `Restore()` сбрасывает `DeletedAt` и порождает `OperationRestored`. Физического удаления операции нет. Удаленная операция не редактируется (ни содержимое, ни перенос на другой кошелек), пока не восстановлена. `UpdatedAt` при удалении и восстановлении не меняется.

### 2.5 Transfer (контекст Operations)

Агрегат из одной сущности `Transfer`, координирующий создание/редактирование/мягкое удаление/восстановление ровно двух связанных `Operation` (списание и зачисление) как единого действия пользователя (раздел 4 требований).

**Жизненный цикл (ADR-0002 §3).** Как и `Operation`, `Transfer` несет `DeletedAt` и `IsDeleted`. `SoftDelete` и `Restore` выполняются над переводом и обеими «ногами» сразу: все три записи получают один и тот же `DeletedAt` (при восстановлении — сбрасывают его), `Transfer` порождает `TransferDeleted`/`TransferRestored`, а «ноги» — свои `OperationDeleted`/`OperationRestored`. Отдельная «нога» через свой агрегат `Operation` ни удалена, ни восстановлена быть не может.

**Граница агрегата — сознательный компромисс.** По строгому DDD одна транзакционная граница = один агрегат, но `Transfer` логически должен согласованно управлять двумя `Operation`, которые сами являются отдельными агрегатами (в собственном контексте, со своим жизненным циклом редактирования как обычных операций). Решение: `Transfer` хранит только `SourceOperationId` и `TargetOperationId` (ссылки, не встроенные сущности); атомарность обеспечивается на уровне прикладного сервиса (Application Service), который в одной БД-транзакции создает/изменяет `Transfer` и оба `Operation`. Это соответствует модульному монолиту с реляционной БД, где реальная ACID-транзакция доступна — при переходе к микросервисам эта граница потребовала бы пересмотра (saga).

### 2.6 BalanceSnapshot (контекст BalanceHistory)

Агрегат из одной сущности `BalanceSnapshot`, идентифицируемый парой `(WalletId, Date)` (уникальность — обязательное требование раздела 5). Хранит рассчитанный баланс кошелька на конкретную дату.

**Граница агрегата:** один слепок (один кошелек, одна дата). Каскадный пересчет (ADR-0003) — это последовательность операций **над множеством** агрегатов `BalanceSnapshot` одного кошелька, оркестрируемая доменным сервисом `BalanceRecalculationService`, а не единая транзакция одного агрегата.

Слепок — производные данные, рассчитанные системой, а не история кошелька (ADR-0002 §1): не существует без кошелька и удаляется вместе с ним (`MarkAsDeleted()` порождает `BalanceSnapshotDeleted`, по одному на слепок). Валюта слепка неизменяема, поэтому при смене валюты кошелька слепки удаляются и создаются заново.

### 2.7 ExchangeRateQuote (контекст ExchangeRates)

Агрегат из одной сущности, представляющий известный курс валютной пары на определенный момент: либо «последний успешно загруженный» (используется для текущих расчетов), либо «исторический на дату» (используется для расчета исторической общей суммы, раздел 5). Идентифицируется парой `(FromCurrencyId, ToCurrencyId)` (ссылки на `Currency` из ReferenceData) для «последнего», либо тройкой `(FromCurrencyId, ToCurrencyId, Date)` для исторических записей.

**Граница агрегата:** один курс одной пары на один момент/дату. Матрица курсов между всеми валютами не хранится и не является агрегатом — только пары, реально запрошенные (активная валюта → текущая основная валюта), согласно ADR-0004 §4, §7.

**История курсов загружается, а не накапливается и не запрашивается при чтении** ([ADR-0004](./adr/0004-currencies-and-exchange-rates.md), §8, §9). Исторические записи заполняет фоновая дозагрузка (`BackfillExchangeRateHistory`) за период от самой ранней `AccountingStartDate` среди **всех** кошельков, включая архивные, (с запасом в несколько дней слева, чтобы для выходного на левой границе нашелся ближайший более ранний курс) до сегодняшнего дня; повторная загрузка того же дня обновляет значение курса (исторические записи — не append-only, выведено при реализации). Чтение (`GetHistoricalRate`) только читает из БД: курс на дату или ближайший более ранний, для той же валюты — 1; к сервису курсов при чтении обращений нет.

**`HistoricalRateCoverage`** — служебная сущность ExchangeRates: для пары `(FromCurrencyId, ToCurrencyId)` хранит непрерывный диапазон дат `[CoveredFrom; CoveredTo]`, по которому история уже загружена. Нужна, чтобы дозагрузка была идемпотентной и возобновляемой: прерванный проход продолжается с места остановки, повторный проход запрашивает только недостающие края, а заведомо пустой ранний период (у сервиса нет данных раньше некоторой даты) не перезапрашивается каждый день. Покрытие не бизнес-понятие и пользователю не показывается; удаляется вместе с валютой и вместе с историей пар к прежней основной валюте.

### 2.8 AuditEntry (контекст Audit)

Агрегат из одной сущности, представляющий одну неизменяемую запись аудита: что изменилось, когда, какая запись затронута, значение до/после, инициатор (User/System). Создается один раз и никогда не изменяется и не удаляется (append-only).

**Граница агрегата:** одна запись аудита. `AuditEntry` не ссылается на другие агрегаты напрямую типами других контекстов — только по паре `(EntityType: string, EntityId: Guid)`, чтобы Audit оставался независимым и не создавал обратных зависимостей от Wallets/Operations/BalanceHistory/ExchangeRates/ReferenceData.

## 3. Сущности

В этой модели почти все агрегаты состоят из единственной сущности (сама сущность = корень агрегата), что типично для предметной области с преимущественно «плоскими» записями:

| Сущность (= корень агрегата) | Контекст |
|---|---|
| `Wallet` | Wallets |
| `WalletType` | ReferenceData |
| `OperationType` | ReferenceData |
| `Currency` | ReferenceData |
| `AvailableCurrency` | ReferenceData (список сервиса курсов, пользователем не редактируется) |
| `OperationBehaviorKind` | ReferenceData (системный, не редактируется пользователем) |
| `Operation` | Operations |
| `Transfer` | Operations |
| `BalanceSnapshot` | BalanceHistory |
| `ExchangeRateQuote` | ExchangeRates |
| `HistoricalRateCoverage` | ExchangeRates (служебная, учет покрытия истории курсов) |
| `AuditEntry` | Audit |

Дочерних сущностей (entity, не являющихся корнем, но живущих внутри агрегата) в модели нет — предметная область не требует составных агрегатов на этом этапе. Если в будущем появится, например, разделение «фактический / доступный баланс» кошелька (раздел 1, явно оставлено не заблокированным на будущее), это может добавить дочерние сущности внутрь `Wallet`, не ломая внешние границы контекста.

## 4. Value Objects

| VO | Состав | Где используется | Назначение |
|---|---|---|---|
| `Money` | `Amount: decimal` (произвольная точность, см. ADR-0005) + `CurrencyId: CurrencyId` (ссылка на элемент справочника `Currency`) | `Wallet.CurrentBalance`, `Wallet.InitialBalance`, `Operation.Amount`, `BalanceSnapshot.Balance` | Неделимая пара «сумма + валюта»; арифметика (сложение/вычитание) допустима только между `Money` с одинаковым `CurrencyId` — попытка смешать валюты запрещена на уровне типа. |
| `ExchangeRateValue` | `decimal` (точность как у Frankfurter, без округления) | `ExchangeRateQuote.Rate` | Отдельный VO, а не `decimal` напрямую — чтобы явно запретить случайную арифметику курса как обычного числа без единиц измерения. |
| `AdjustmentInput` | `Mode: Absolute \| Delta` + `Value: Money` | `Operation` (только для операций с поведением Adjustment) | Формализует решение Q3: пользователь либо задает новое абсолютное значение баланса, либо дельту; хранится именно выбор пользователя, а не заранее вычисленная дельта — это необходимо для корректного каскадного пересчета (см. ADR-0003, инвариант ниже). |
| `AuditActor` | `Kind: User \| System` (+ опционально `SystemProcessName` для System) | `AuditEntry.Actor` | Кто инициировал изменение — пользователь или фоновый процесс. |
| `AuditFieldChange` | `FieldName: string` + `OldValue: string?` + `NewValue: string?` | `AuditEntry.Changes` (коллекция VO) | Представление одного измененного поля записи для журнала аудита. |
| `DisplayOrder` | `int` (порядковое значение) | `Wallet.DisplayOrder` | Простая обертка для ручного порядка отображения; не требует уникальности между кошельками. |

Строго типизированные ID (`WalletId`, `OperationId`, `TransferId`, `BalanceSnapshotId`, `WalletTypeId`, `OperationTypeId`, `CurrencyId`, `OperationBehaviorKindId`, `AuditEntryId`) также являются value objects (по одному `Guid`-полю каждый), см. «Общие соглашения».

## 5. Инварианты

### Wallet
- В системе всегда существует ровно один кошелек с `IsPrimary = true` (решено, Q7) — обеспечивается `PrimaryWalletPolicy`, а не самим агрегатом.
- `IsPrimary = true` ⇒ `IncludeInTotal = true`, и это значение нельзя выключить, пока кошелек остается основным (решено, Q8).
- Нельзя установить `IsArchived = true`, если `IsPrimary = true` (решено, Q7) — сначала нужно назначить другой кошелек основным.
- **История кошелька — только `Operation`**, включая мягко удаленные и обе «ноги» переводов (ADR-0002 §2). `BalanceSnapshot`, ненулевой `InitialBalance` и заявленные балансы (ADR-0003 §6) историей не считаются.
- `Currency` неизменяема, если у кошелька есть хотя бы одна `Operation`, включая мягко удаленную (решено, Q15; уточнено ADR-0002). `BalanceSnapshot` смену валюты не блокирует: слепки кошелька удаляются и перестраиваются в новой валюте.
- Валюта кошелька при создании выбирается из `AvailableCurrency` и автоматически становится активной (создается `Currency`, если ее еще нет); при смене валюты кошелька новая валюта должна быть **активной** (существующей `Currency`; выведено при реализации из ADR-0004 §7, отдельно с пользователем не обсуждалось). Кошелек не может ссылаться на несуществующую валюту.
- Кошелек нельзя удалить физически, если у него есть хотя бы одна `Operation` (включая мягко удаленную) — только архивировать (решено, Q2; уточнено ADR-0002). Кошелек без `Operation` удаляется физически вместе со всеми своими `BalanceSnapshot`.
- Основной кошелек нельзя ни удалить, ни архивировать, пока он основной.
- Архивный кошелек исключен из активных списков, но его история и слепки сохраняются, он участвует в исторической общей сумме.

### WalletType / OperationType / Currency
- Элемент справочника `WalletType`/`OperationType`, **используемый** существующими `Wallet` (включая архивные) или `Operation` (включая мягко удаленные), нельзя удалить физически — только деактивировать (решено, Q11). Неиспользуемый элемент удаляется физически.
- **`Currency` не деактивируется** (ADR-0002 §4, ADR-0004 §7): валюта либо активна (запись существует), либо нет. Валюту, **используемую** существующими `Wallet` (включая архивные) или `Operation` (включая мягко удаленные), нельзя убрать из активных; неиспользуемая удаляется физически вместе с ее `ExchangeRateQuote` (обе стороны пары, последние и исторические) и `HistoricalRateCoverage`. Записи `ExchangeRateQuote` использованием не считаются (ADR-0002 §4).
- Код `Currency` уникален. Добавить в активные можно только код, присутствующий среди `AvailableCurrency` (произвольный код и криптовалюты отклоняются); уже активный код повторно не добавляется. Название создаваемой `Currency` берется из `AvailableCurrency`.
- `AvailableCurrency`: код уникален; список заменяется целиком по ответу сервиса. Пустой ответ, ошибка или неразборчивое тело сервиса **не изменяют** список (защита от стирания списка при сбое источника). Отсутствие кода в обновленном списке не влияет на активную `Currency` с этим кодом.
- `OperationType.BehaviorKindId` неизменяем после создания элемента — смена базового поведения задним числом изменила бы смысл всех уже существующих операций этого типа.

### OperationBehaviorKind
- Набор строк системный: создание, изменение и удаление элементов недоступно пользователю через API/UI — только через миграцию/seed при обновлении приложения (решено при проектировании домена).

### Operation
- `Operation.Amount.CurrencyId` должен совпадать с валютой кошелька (`Wallet.CurrencyId`), на который ссылается `Operation.WalletId` — операция не может менять валюту при вводе.
- `Operation.OperationTypeId` должен ссылаться на активный (не деактивированный) элемент справочника **на момент создания** операции; уже существующие операции могут продолжать ссылаться на впоследствии деактивированный тип.
- Операцию, у которой заполнен `TransferId` (часть перевода), нельзя удалить, восстановить или изменить в обход агрегата `Transfer` — только как часть операции над `Transfer` целиком.
- **Операция удаляется только мягко, с любой датой** (ADR-0002 §3, решение пользователя 2026-09-30): физического удаления нет. `SoftDelete()` допустим только для не удаленной операции, `Restore()` — только для удаленной; повторные вызовы отклоняются.
- **Удаленная операция** (`DeletedAt` заполнено) не редактируется и не переносится на другой кошелек, пока не восстановлена. Она остается в списках всегда; не участвует в расчете `Wallet.CurrentBalance`, `BalanceSnapshot`, общей суммы и корректирующих сумм; входит в историю кошелька и считается использованием элемента справочника.
- Восстановление возможно всегда: повторная проверка даты, активности типа операции и архивности кошелька не выполняется.
- Системная корректирующая сумма (ADR-0003 §6) мягкому удалению не подлежит.
- `AdjustmentInput` заполнен тогда и только тогда, когда `OperationType`, на который ссылается операция, имеет `BehaviorKindId = Adjustment`.

### Transfer
- `SourceWalletId ≠ TargetWalletId`.
- Валюта `SourceWallet` и `TargetWallet` должна совпадать на момент создания перевода (раздел 4 требований).
- Сумма списания (`SourceOperation.Amount`) всегда равна сумме зачисления (`TargetOperation.Amount`) — комиссия за перевод между своими кошельками не поддерживается (решено, Q10).
- `Transfer` не может существовать без обеих связанных `Operation`; мягкое удаление и восстановление перевода обязаны затрагивать перевод и обе его операции атомарно, с одним общим `DeletedAt`. Отдельную «ногу» удалить или восстановить нельзя.
- `SoftDelete` допустим только для не удаленного перевода, `Restore` — только для удаленного.

### BalanceSnapshot
- Уникальность пары `(WalletId, Date)` — не более одной записи (явное требование раздела 5).
- Баланс на дату раньше `Wallet.AccountingStartDate` считается равным нулю и **не материализуется** отдельным `BalanceSnapshot` (решено, Q13) — снепшоты существуют только начиная с `AccountingStartDate`.
- Любое изменение операции/корректировки, затрагивающее прошедшую дату (включая мягкое удаление и восстановление операции или перевода), обязано инициировать пересчет данного и всех последующих слепков вплоть до сегодняшнего дня (решено, Q4) — частичный пересчет запрещен. Мягко удаленные операции в баланс слепка не входят.
- Слепок не существует без кошелька: при физическом удалении кошелька все его слепки удаляются в той же транзакции; при смене валюты кошелька — удаляются и создаются заново (валюта слепка неизменяема).
- Пропущенный плановый запуск (12:00 UTC) обязан быть досоздан при следующем старте приложения, без пробелов в датах (решено, Q12).

### ExchangeRateQuote
- `Rate > 0`.
- `LastSuccessfulUpdate` (метка времени) обновляется только при успешном ответе от Frankfurter; при ошибке сохраняется прежнее значение курса и метки времени (явное требование раздела 2).
- Периодичность планового автообновления — 1 раз в сутки; ручное обновление сбрасывает таймер автообновления заново (решено, Q5; отклонение от исходного текста требований, см. ADR-0004).
- Пары существуют только вида «активная валюта → валюта текущего основного кошелька»; обе валюты — существующие `Currency`; валюта с самой собой не образует пары. Курсы пар к прежней основной валюте после смены основного кошелька удаляются (последние — при следующем обновлении, исторические и покрытие — в конце прохода дозагрузки).
- Чтение курсов (последних и исторических) — только из БД; обращение к сервису курсов в момент чтения запрещено (ADR-0004 §8).
- `HistoricalRateCoverage`: `CoveredFrom <= CoveredTo`; `FromCurrencyId ≠ ToCurrencyId`; одна запись на пару; диапазон непрерывный — исторические записи пары покрывают его без пропусков, кроме выходных и праздников, у которых курса нет (используется ближайший более ранний). Диапазон расширяется влево (более ранняя `AccountingStartDate`) и вправо (до сегодняшнего дня, ежедневно). Если у сервиса нет данных раньше некоторой даты, левая граница считается достигнутой.
- Дозагрузка идемпотентна: повторный проход без новых данных не создает дублей и запрашивает не больше одного правого края на пару; сбой источника прерывает проход, сохраненное остается, следующий проход продолжает.
- Пока дозагрузка пары не завершена, исторические курсы за часть дат отсутствуют; Reporting исключает кошельки без курса из исторической суммы с указанием причины (ADR-0004 §9).

### AuditEntry
- Запись аудита неизменяема после создания: не редактируется и не удаляется никаким сценарием системы (явное требование раздела 6 — «история аудита не должна теряться»).
- Любое мутирующее действие в контекстах Wallets, ReferenceData, Operations, BalanceHistory, ExchangeRates обязано породить не менее одной `AuditEntry` в той же транзакции, что и само изменение.

## 6. Доменные операции (команды) и доменные события

Событие порождается агрегатом-инициатором и обрабатывается: (а) собственным контекстом при необходимости побочных эффектов, (б) контекстом Audit — всегда, (в) контекстом BalanceHistory — для событий, влияющих на баланс. Обработка происходит синхронно, в одной базе-транзакции с командой (это архитектурное решение будет закреплено на этапе «Высокоуровневая архитектура»).

### Wallets

| Команда | Событие | Побочные эффекты (подписчики) |
|---|---|---|
| `CreateWallet` | `WalletCreated` | Audit: запись создания. Если кошелек первый в системе — `PrimaryWalletPolicy` автоматически делает его основным (решено, Q7) и порождает `PrimaryWalletChanged`. Валюта указывается кодом из доступных: если она еще не активна, в той же транзакции выполняется `ActivateCurrency` (`CurrencyCreated`, Audit: `Currency`/`Created`); код ни активный, ни доступный — отклонение, валюта не создается; при отклонении создания кошелька активация откатывается (ADR-0004 §7). ExchangeRates: дата начала учета может оказаться раньше текущей самой ранней — расширение истории курсов (ADR-0004 §9). |
| `UpdateWallet` | `WalletUpdated` | Audit: запись изменения (до/после). |
| `ArchiveWallet` | `WalletArchived` | Audit. Отклоняется, если кошелек основной (Q7). |
| `DeleteWallet` | `WalletDeleted` | Audit. BalanceHistory: удаляет все слепки кошелька в той же транзакции (`BalanceSnapshotDeleted` по одному на слепок, каждый — в Audit со значением до удаления). Отклоняется, если есть история — операции, включая мягко удаленные (Q2, ADR-0002) — или кошелек основной. |
| `SetPrimaryWallet` | `PrimaryWalletChanged` | Audit. `PrimaryWalletPolicy` снимает флаг со старого основного, ставит новому `IncludeInTotal = true` принудительно (Q8). Reporting инвалидирует кэш пересчета общей суммы (если есть). ExchangeRates: перезапрос курсов с новой базовой валютой и повторная загрузка истории курсов ко всем активным валютам к новой основной (ADR-0004 §5, §9). |
| `ChangeWalletCurrency` | `WalletCurrencyChanged` | Audit. BalanceHistory: удаляет слепки кошелька и перестраивает их в новой валюте от `AccountingStartDate`. Отклоняется, если есть история — операции, включая мягко удаленные (Q15, ADR-0002), либо новая валюта не существует среди активных (выведено при реализации, ADR-0004 §7). ExchangeRates: если кошелек основной, меняется основная валюта — курсы и история перезагружаются, как при `SetPrimaryWallet` (выведено при реализации из ADR-0004 §5, §9). |

### ReferenceData

| Команда | Событие | Побочные эффекты |
|---|---|---|
| `CreateWalletType` / `CreateOperationType` | `WalletTypeCreated` / `OperationTypeCreated` | Audit. |
| `ActivateCurrency` (бывш. `CreateCurrency`; из доступных; также внутри `CreateWallet`) | `CurrencyCreated` («добавлена в активные») | Audit. ExchangeRates: догрузка курса и истории новой валюты в фоне, после фиксации транзакции (ADR-0004 §9). Отклоняется: код не среди доступных — ошибка запроса; код уже активен — конфликт. |
| `RenameCurrency` (реакция на обновление списка доступных, System) | `CurrencyRenamed` | Audit: `Updated` (изменение `Name`), актор — инициатор прогона обновления. Событие только при реальном изменении названия. |
| `DeactivateWalletType` / `DeactivateOperationType` | `WalletTypeDeactivated` / `OperationTypeDeactivated` | Audit. (`DeactivateCurrency` и `CurrencyDeactivated` удалены: у валюты нет состояния «деактивирована», ADR-0004 §7.) |
| `DeleteWalletType` / `DeleteOperationType` | `WalletTypeDeleted` / `OperationTypeDeleted` | Audit. Отклоняется, если используется — есть ссылки от кошельков или операций, включая мягко удаленные (Q11, ADR-0002 §4). |
| `DeleteCurrency` («убрать из активных») | `CurrencyDeleted` | Audit. Отклоняется, если используется — есть ссылки от кошельков или операций, включая мягко удаленные; курсы валют использованием не считаются (Q11, ADR-0002 §4). ExchangeRates удаляет курсы валюты (последние и исторические, обе стороны пары) и ее покрытие истории в той же транзакции. Валюта остается среди доступных. |
| `ReplaceAvailableCurrencies` (System/User — по инициатору прогона обновления курсов; порт ReferenceData, вызывается из ExchangeRates) | — (событий нет; список не аудитируется — это каталог сервиса, не запись пользователя) | Полная замена списка по ответу сервиса; названия активных валют, коды которых есть в ответе, приводятся к названиям сервиса (`CurrencyRenamed`). Пустой ответ — не применяется. |

`OperationBehaviorKind` не имеет пользовательских команд — набор строк фиксируется миграцией/seed-данными при развертывании (см. инвариант выше).

### Operations

| Команда | Событие | Побочные эффекты |
|---|---|---|
| `CreateOperation` (Income/Expense/Adjustment) | `OperationCreated` | Audit. Wallets: обновление `CurrentBalance`. BalanceHistory: пересчет слепков с даты операции (ADR-0003). |
| `UpdateOperation` | `OperationUpdated` | Отклоняется, если операция часть перевода или мягко удалена. Audit (до/после, включая смену `walletId`). Wallets: пересчет `CurrentBalance`. BalanceHistory: каскадный пересчет с наименьшей из старой/новой даты операции (Q4) — если `walletId` не изменился; при смене кошелька (UC-13, решение пользователя от 2026-09-11) пересчитываются ОБА кошелька независимо (`PreviousWalletId` события) — старый с прежней даты операции, новый с новой. |
| `DeleteOperation` (мягкое удаление, любая дата) | `OperationDeleted` | Audit (значение до изменения; изменяется `DeletedAt`). Wallets: из `CurrentBalance` вычитается примененная дельта. BalanceHistory: каскадный пересчет с даты удаленной операции. Отклоняется, если `TransferId` заполнен ИЛИ операция уже удалена (см. инварианты Operation, ADR-0002). Физического удаления нет. |
| `RestoreOperation` | `OperationRestored` | Audit (изменяется `DeletedAt`). Wallets: примененная дельта снова добавляется к `CurrentBalance`. BalanceHistory: каскадный пересчет с даты операции. Отклоняется, если `TransferId` заполнен ИЛИ операция не удалена. |
| `CreateTransfer` | `TransferCreated` (+ два `OperationCreated`) | То же, что `OperationCreated`, но для обоих кошельков одновременно, в одной транзакции. |
| `DeleteTransfer` (мягкое удаление, любая дата) | `TransferDeleted` (+ два `OperationDeleted`) | То же, что `OperationDeleted`, но для обоих кошельков одновременно; перевод и обе «ноги» получают один `DeletedAt`. Отклоняется, если перевод уже удален. |
| `RestoreTransfer` | `TransferRestored` (+ два `OperationRestored`) | То же, что `OperationRestored`, но для обоих кошельков одновременно; `DeletedAt` сбрасывается у перевода и обеих «ног». Отклоняется, если перевод не удален. |

BalanceHistory реагирует на события операций («ног» перевода в том числе), а не на `TransferDeleted`/`TransferRestored`: два кошелька перевода пересчитываются через события его «ног».

### BalanceHistory

| Команда | Событие | Побочные эффекты |
|---|---|---|
| `CreateOrUpdateDailySnapshot` (плановая, System) | `BalanceSnapshotCreated` / `BalanceSnapshotUpdated` | Audit. |
| `RecalculateBalanceHistoryFrom(walletId, fromDate)` (внутренняя, вызывается обработчиками событий Operations: создание, изменение, мягкое удаление, восстановление) | по одному `BalanceSnapshotUpdated` на каждую пересчитанную дату | Audit — по одной записи на каждый обновленный слепок (соответствует требованию раздела 6: «обновление слепка баланса» — отслеживаемое действие). |

### ExchangeRates

| Команда | Событие | Побочные эффекты |
|---|---|---|
| `RefreshExchangeRates` (старт приложения, плановая раз в сутки, по кнопке, по сигналу о смене основной валюты) | `ExchangeRatesUpdated` (успех) / `ExchangeRateUpdateFailed` (ошибка) | Первым шагом загружает и сохраняет список доступных валют (`ReplaceAvailableCurrencies`) — **в том числе без основного кошелька**; затем курсы пар «активная валюта → основная» (без основного кошелька курсы не обновляются). При ошибке `LastSuccessfulUpdate` не меняется (явное требование раздела 2); при ошибке или пустом ответе по списку валют список остается прежним. |
| `BackfillExchangeRateHistory` (System, в фоне; не выполняется внутри HTTP-запроса пользователя) | `ExchangeRateHistoryLoaded` — одно событие на проход, в котором что-либо загружено или произошел сбой (загруженные диапазоны и сбойные пары) | Audit: запись `HistoryLoaded` (батчевая, по образцу `ExchangeRatesUpdated`). Для каждой активной валюты, кроме основной, догружает курсы к основной за период `[самая ранняя AccountingStartDate среди всех кошельков, включая архивные, с запасом слева; сегодня]`, расширяя `HistoricalRateCoverage` влево и вправо; прерванный проход продолжается с места остановки. Без основного кошелька не выполняется. Удаляет историю и покрытие пар не к текущей основной валюте и пар с неактивной валютой. |
| — (реакция на `CurrencyCreated`, `WalletCreated`, `WalletCurrencyChanged`, `PrimaryWalletChanged`) | — | Сигнал фоновому сервису запустить обновление курсов и дозагрузку истории. Запрос исторического курса при чтении (`GetOrFetchHistoricalRate`) упразднен: Reporting читает исторические курсы только из БД (`GetHistoricalRate`, ADR-0004 §8).

### Audit

Audit не имеет собственных пользовательских команд — только один обработчик `RecordAuditEntry`, подписанный на все события выше, плюс read-модель для UC-25 (просмотр истории изменений записи).

## Решения, принятые при формализации домена

Эти три пункта не были частью бизнес-требований и возникли только при проектировании DDD-модели; все три подтверждены пользователем перед фиксацией в модели:

1. **Справочник валют.** `Currency` — отдельный справочник пользователя (контекст ReferenceData), а не закрытый список в коде. *Изменено [ADR-0004](./adr/0004-currencies-and-exchange-rates.md), §7, решение пользователя 2026-09-30:* изначально — «по той же схеме, что `WalletType`/`OperationType` (создание, деактивация при использовании, удаление если не используется), произвольные валюты, включая криптовалюты». Теперь `Currency` — **активная** валюта: добавляется только из списка доступных валют сервиса курсов (`AvailableCurrency`), произвольные коды и криптовалюты не принимаются, состояния «деактивирована» нет — используемую валюту убрать из активных нельзя, неиспользуемая удаляется. Это не меняет «валюта — запись справочника, а не enum»; меняется источник допустимых значений.
2. **`OperationBehaviorKind` — таблица, а не enum в коде.** Четыре базовых вида поведения операции (Income/Expense/Transfer/Adjustment) хранятся как системный справочник в БД, а не как закрытый enum в C#. В отличие от пользовательских справочников, строки этой таблицы не редактируются через API/UI — только сеются при развертывании, так как добавление нового вида поведения требует кода, который умеет его интерпретировать (раздел 3 требований).
3. **Правило удаления операции.** Первоначальное ограничение удаления операции по дате отменено решением пользователя от 2026-09-30: операции и переводы удаляются только мягко (`DeletedAt`), с любой датой, и могут быть восстановлены; удаленная запись остается в списке и не участвует в расчетах. Физического удаления операций нет, история кошелька — только операции, включая мягко удаленные. Правило зафиксировано в [ADR-0002](./adr/0002-record-lifecycle.md).
