# ADR-0002: Политика удаления против архивирования/деактивации

## Статус

Принято

## Контекст

Исходные бизнес-требования (раздел 1) прямо предписывают архивирование вместо удаления только для одного случая — «удалять кошелек с историей операций не нужно». Раздел 6 (аудит) при этом упоминает «удаление или отмену» как отдельно отслеживаемое действие, а раздел 7 вводит расширяемые справочники (типы кошельков, типы операций), не уточняя их жизненный цикл. Это порождало неоднозначность (открытые вопросы Q2 и Q11 в [user-scenarios.md](../../requirements/user-scenarios.md)): что именно можно удалять окончательно, а что — только скрывать/деактивировать.

Ответы пользователя дали единый принцип, применимый сразу к нескольким типам сущностей: кошелькам, операциям и элементам справочников.

## Решение

Единое правило для всех перечисленных сущностей: **если у сущности есть связанные данные (история), она не удаляется физически, а только помечается как неактивная; если связанных данных нет — сущность можно удалить окончательно.**

Конкретно:

- **Wallet** — кошелек с историей операций/слепков баланса архивируется (не удаляется); кошелек без истории удаляется окончательно (решено, Q2).
- **Operation** — операцию нельзя удалить физически, если (а) она часть перевода (`TransferId` заполнен) **или** (б) её дата ≤ дате последнего существующего слепка баланса (`BalanceSnapshot`) этого кошелька — то есть операция уже учтена в зафиксированной истории баланса. Такую операцию можно только редактировать (с каскадным пересчетом слепков, см. ADR-0003), но не удалить бесследно. Операцию без этих связей — датированную позже последнего слепка (обычно сегодняшним числом, до планового запуска 12:00 UTC) и не входящую в перевод — можно удалить физически, с фиксацией в аудите значения записи до удаления и каскадным пересчетом затронутых слепков (см. ADR-0003). *(Уточнено при проектировании DDD-модели, см. [ddd-model.md](../ddd-model.md#решения-принятые-при-формализации-домена); первая версия этого ADR оставляла точную границу как открытый пункт.)*
- **Reference dictionary item** (тип кошелька, тип операции, валюта) — элемент, уже используемый существующими записями, деактивируется (скрывается из выбора для новых записей), но не удаляется; неиспользуемый элемент можно удалить окончательно (решено, Q11, по аналогии с кошельками). Справочник `Currency` добавлен при проектировании домена по этой же схеме (см. `ddd-model.md`); справочник `OperationBehaviorKind` — исключение: он системный, недоступен пользователю для редактирования и не подчиняется этому правилу удаления/деактивации.

Технически это означает, что в модели данных для этих трех типов сущностей нужен явный признак активности/архивности (например, `IsArchived` / `IsActive`), а не полагаться только на физическое удаление строки.

## Последствия

- Единообразный паттерн упрощает доменную модель: одна и та же логика проверки «есть ли связанные данные» применяется к трем разным сущностям.
- Для Wallet «связанные данные» — наличие операций/слепков; для Operation — участие в переводе или дата ≤ последнего слепка кошелька; для элементов справочника — использование хотя бы одной записью. Все три определения зафиксированы выше и в `ddd-model.md`.
- Правило по Operation вводит асимметрию между «редактировать» и «удалить»: пользователь всегда может исправить историческую операцию (сумму, дату и т.д.) с каскадным пересчетом, но не может физически стереть её след из истории, если она уже отражена в зафиксированном слепке баланса. Это сознательный выбор в пользу прослеживаемости истории, а не техническое ограничение.
- Аудит должен одинаково фиксировать оба вида «исчезновения» записи — физическое удаление и деактивацию/архивирование — с сохранением значения записи до изменения (согласовано с разделом 6 требований).
- Индексы/фильтры на уровне запросов должны по умолчанию скрывать архивные/деактивированные записи из «активных» списков, но обеспечивать их видимость в истории/отчетах.

## Альтернативы

- **Полный soft-delete для всех сущностей без исключений** (никогда не удалять физически) — отклонено пользователем: явно подтверждено, что кошельки и операции без истории/связей можно удалять окончательно (Q2).
- **Полное физическое удаление везде, без архивирования** — отклонено требованиями раздела 1 (архивирование прямо предписано для кошельков с историей) и ответом на Q11 для справочников.
- **Отдельный механизм «закрытия периода»** (явная пользовательская пометка даты/периода как неизменяемого) — отклонено пользователем как избыточное новое понятие; вместо этого граница определяется автоматически через факт существования слепка баланса на дату операции.
