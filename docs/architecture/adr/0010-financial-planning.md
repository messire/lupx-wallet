# ADR-0010: Финансовое планирование — долги, фонды, бюджеты, плановые операции, прогноз

## Статус

**Предложено (2026-11-14).** Ждёт ответов владельца на вопросы В1–В8 (раздел «Открытые вопросы»). До их закрытия реализация issues #6–#13 не начинается — так требуют issue #5 («ADR и доменная модель согласованы до реализации») и раздел 10 бизнес-требований.

**Состояние реализации:** не реализовано.

## Контекст

Issues #5–#13 (v0.4.0) добавляют область, которую раздел 8 требований v1 явно исключал из первого этапа: бюджеты, регулярные платежи, долги, кредитные продукты, а раздел 1 — разделение фактического и доступного баланса. Тот же раздел 1 требовал не блокировать такое развитие архитектурно; текущая модель (модули с собственными схемами, связь по Id и событиям, [ADR-0001](./0001-modular-monolith.md)) это позволяет без изменения существующих агрегатов.

Сквозные требования из issues:

- **Нет двойного учёта.** Реальные деньги — только баланс `Wallet`, который меняют только фактические операции (`Operation`). Долг, фонд, бюджет и план деньги не создают и не списывают (#5, #6, #7, #9).
- **Связь с фактом.** Погашение долга и исполнение плана связываются с реальной операцией, а не дублируют её (#6, #8, #9).
- **Мультивалютность.** Где суммы разных валют сводятся вместе, явно показываются валюта расчёта, дата и источник курса (#10, #12).

## Решение

### 1. Различие понятий

| Понятие | Что это | Меняет баланс кошелька? |
|---|---|---|
| `Wallet` | Где лежат реальные деньги | Да — через операции |
| `Liability` (долг, кредит) | Сколько и кому вы должны; остаток и график платежей | Нет. Погашение — обычная операция расхода со ссылкой на долг |
| `Fund` (фонд) | Часть реальных денег кошельков, отложенная под цель | Нет. Резерв — пометка «эти деньги заняты» |
| `Budget` (бюджет) | Лимит расходов на месяц по категориям | Нет. Ничего не резервирует, только сравнивает факт с лимитом |
| `PlannedTransaction` (плановая операция) | Будущий доход или расход, разовый или повторяющийся | Нет, пока не исполнен. Исполнение создаёт обычную операцию |

### 2. Новые модули (bounded contexts)

По одному модулю и одной схеме БД на контекст (ADR-0001, ADR-0007): `Debts`, `Funds`, `Budgeting`, `Planning`. Модуль `Reporting` (read-only) расширяется прогнозом и свободными средствами. Новые агрегаты публикуют доменные события, Audit подписывается на них по общему механизму ([ADR-0006](./0006-audit.md)).

```
Debts      ──Id──▶ ReferenceData (Currency), Operations (OperationId платежа)
Funds      ──Id──▶ Wallets (WalletId резерва), Debts (необязательный LiabilityId)
Budgeting  ──Id──▶ ReferenceData (OperationTypeId категории, Currency)
Planning   ──Id──▶ ReferenceData (OperationTypeId, Currency), Wallets (WalletId), Operations (OperationId исполнения)
Operations ──событие──▶ Debts, Planning   (мягкое удаление/восстановление/изменение операции, на которую ссылается платёж или исполнение)
Funds      ──запрос──▶ Wallets            (текущий баланс кошелька при резервировании)
Budgeting  ──запрос──▶ Operations, ExchangeRates (фактические расходы за период, курсы)
Reporting  ──запрос──▶ Wallets, Funds, Debts, Planning, ExchangeRates (прогноз, свободные средства)
Debts, Funds, Budgeting, Planning ──событие──▶ Audit
```

### 3. Debts — долги и кредиты (#6, #8)

- **`Creditor`** — справочник кредиторов модуля (название; деактивация, если используется — по правилам [ADR-0002](./0002-record-lifecycle.md) §4). Нужен для разбивки долга по кредиторам; число кредиторов не ограничено.
- **Агрегат `Liability`** *(В2-А)*: `CreditorId`, название, валюта, исходная сумма, дата возникновения, статус (`Active`, `Repaid`, `Cancelled`), необязательные справочные условия (ставка, срок) *(В5-А)*. Остаток = исходная сумма − сумма основной части учтённых платежей; не хранится отдельно от платежей.
- **`ScheduledPayment`** (сущность внутри `Liability`, только у кредита с графиком): дата, основная часть, проценты. Перенос даты, изменение условий — правка графика. Статус платежа вычисляется: оплачен / частично / просрочен (дата < сегодня и не оплачен полностью) / ожидается.
- **`LiabilityPayment`** (сущность внутри `Liability`): ссылка на `OperationId` фактического расхода, основная часть, проценты *(В4-А, В5-А)*. Сумма платежа = сумма операции; уменьшает остаток только основная часть. Платёж сверяется с ближайшим неоплаченным `ScheduledPayment` (частичное погашение — частичная оплата пункта графика).
- **Погашение:** пользователь создаёт обычный расход из кошелька в валюте долга, указав долг. Расход проходит через Operations как есть (баланс, история, аудит); Debts хранит только связь. Мягкое удаление операции → платёж перестаёт учитываться (событие `OperationDeleted`), восстановление — снова учитывается.
- **Возникновение долга** *(В3-А)*: долг заводится сам по себе, поступление денег, если нужно, — отдельная операция дохода. Задолженность, которую должны вам, в объём не входит (issues её не упоминают).

### 4. Funds — фонды и резервирование (#7)

- **Агрегат `Fund`**: название, целевая сумма, валюта *(В6-А: одна валюта)*, необязательный `LiabilityId` (фонд на погашение долга), статус (`Active`, `Closed`).
- **`FundAllocation`** (сущность внутри `Fund`): `WalletId` + зарезервированная сумма. Кошелёк — в валюте фонда *(В6-А)*. Резерв = сумма аллокаций; прогресс = резерв / цель.
- **Инвариант без двойного резервирования:** сумма аллокаций всех активных фондов по одному кошельку ≤ текущему балансу кошелька **в момент резервирования**. Проверяет доменный сервис `ReservationPolicy` в транзакции команды, читая баланс через контракт Wallets и аллокации всех фондов (коллекционный инвариант, как `PrimaryWalletPolicy`).
- **Баланс ниже резерва после расходов** *(В7-А)*: фактические операции не блокируются; кошелёк и фонд показывают предупреждение «резерв превышает баланс».
- Снятие резерва уменьшает аллокацию; закрытие фонда снимает все аллокации. Архивирование кошелька с резервом запрещено, пока резерв не снят.
- Сумма реальных балансов при резервировании не меняется — критерий #7 выполняется по построению.

### 5. Budgeting — месячные бюджеты (#11)

- **Агрегат `Budget`**: месяц (`YYYY-MM`), валюта; уникален на пару (месяц, валюта).
- **`CategoryLimit`** (сущность внутри `Budget`): категория + лимит. Категория = `OperationType` с поведением `Expense` *(В1-А)*.
- **Исполнение** (запрос): факт по категории = сумма не удалённых расходов этого типа с датой в месяце по всем кошелькам; операции в другой валюте пересчитываются по курсу на дату операции *(В8-А)*, при отсутствии точного — последний известный на ту дату (как ADR-0004 §8). Остаток = лимит − факт; превышение — отрицательный остаток. Расходы без лимита показываются строкой «Без бюджета».
- **Перенос остатка** на следующий месяц в v0.4.0 не делается: issue #11 откладывает это правило *(В8)*.

### 6. Planning — плановые операции (#9)

- **Агрегат `PlannedTransaction`**: `OperationTypeId` (поведение `Income` или `Expense`), сумма, валюта, необязательный `WalletId` (в валюте плана), описание, дата первого наступления, необязательное `RecurrenceRule`, статус (`Active`, `Finished`).
- **`RecurrenceRule`** (VO): частота `Daily | Weekly | Monthly | Yearly`, интервал N, окончание — нет / до даты / после K повторов. Для `Monthly` число месяца; если в месяце его нет — последний день месяца. *(Предложение, бизнес-деталь — подтверждается на ревью.)*
- **Наступления** вычисляются из правила, не хранятся. Хранятся только отклонения — **`OccurrenceOverride`**: дата наступления + действие `Skip` (пропуск), `Move` (перенос на другую дату) или изменённая сумма.
- **`OccurrenceExecution`**: дата наступления + `OperationId` + исполненная сумма. Исполнение создаёт обычную операцию через Operations (форма предзаполнена из плана). Частичное исполнение: наступление остаётся ожидаемым на остаток, пока его не исполнят полностью или не пропустят *(предложение)*. Удаление операции исполнения (мягкое) возвращает наступление в ожидаемые.
- До исполнения план не влияет ни на баланс, ни на историю баланса.
- Плановые переводы в объём не входят (issue #9 говорит о доходах и расходах).

### 7. Reporting — прогноз и свободные средства (#10, #12)

- **`CashFlowForecast`** (read model, не хранится): по дням от сегодня до горизонта (по умолчанию 3 месяца, выбор 1/3/6/12 — *предложение*). Начальная точка — текущие балансы кошельков с признаком «в общей сумме». Движения: ожидаемые наступления плановых операций (с учётом пропусков, переносов, частичного исполнения) и неоплаченные платежи графиков кредитов. Результат: ожидаемый остаток на каждую дату, отмеченные отрицательные периоды, валюта расчёта = валюта основного кошелька.
- **Курсы в прогнозе:** последний известный курс; в ответе — дата курса и источник (Frankfurter). Будущее изменение курса не моделируется — это явное предположение, оно выводится в UI.
- **Без двойного счёта кредитного платежа:** единственный источник плановых платежей по кредиту — его график. Плановую операцию нельзя связать с долгом; погашение по графику исполняется как платёж долга (п. 3). Просроченный неоплаченный платёж попадает в прогноз на сегодня.
- **Свободные средства** (#12): по кошельку — фактический баланс, зарезервировано (аллокации фондов), свободно = факт − резерв. Сводка — то же в валюте основного кошелька с датой и источником курса. Ближайшие платежи (плановые расходы и платежи графиков на 30 дней) показываются отдельным списком и **не** вычитаются из свободных средств.

### 8. Жизненный цикл и аудит

- Долг с платежами, фонд с историей аллокаций, план с исполнениями физически не удаляются — переводятся в конечный статус (`Cancelled`, `Closed`, `Finished`). Без связанных данных — удаляются физически (по образцу ADR-0002).
- Все изменения пишутся в аудит через diff `ChangeTracker` (ADR-0006 §1). Аллокации, платежи, отклонения и исполнения — дочерние сущности: их изменения попадают в запись агрегата-владельца.
- Денежные суммы — произвольной точности, строками в API ([ADR-0005](./0005-money-precision.md)).

## Открытые вопросы

Отмечены в тексте как *(Вn-А)* — рекомендованный вариант, на котором построено предложение.

| № | Вопрос | Рекомендация |
|---|---|---|
| В1 | Категория бюджета | А: тип операции с поведением «расход». Б: новый справочник категорий, группирующий типы |
| В2 | Долг и кредит | А: одна сущность `Liability`, кредит — с графиком. Б: две сущности |
| В3 | Возникновение долга | А: только запись долга, поступление — отдельной операцией. Б: опционально создавать доход в кошелёк |
| В4 | Погашение | А: расход из кошелька в валюте долга. Б: любой кошелёк, зачёт в валюте долга вручную |
| В5 | Проценты | А: не рассчитываются; график вручную или равными долями, ставка справочно, в платеже можно выделить проценты. Б: расчёт аннуитета/дифференцированного графика |
| В6 | Валюты фонда | А: одна валюта, резерв только из кошельков этой валюты. Б: любые кошельки с пересчётом по курсу |
| В7 | Баланс ниже резерва | А: не блокировать, предупреждать. Б: запрещать такие расходы |
| В8 | Бюджет: валюты и перенос | А: пересчёт по курсу на дату операции, без переноса остатка. Б: только расходы в валюте бюджета |

## Последствия

- Четыре новых модуля по структуре ADR-0007 и четыре новые схемы БД; существующие таблицы не меняются. Новая связь Operations → Debts/Planning только через события и Id.
- В Operations нужен контракт создания операции для исполнения плана и погашения долга (или UI создаёт операцию обычным API и передаёт `OperationId`) — выбирается при реализации, бизнес-правил не меняет.
- Прогноз и свободные средства считаются при запросе; для одного пользователя с сотнями плановых операций это дёшево, кэш не нужен.

## Отклонённые варианты

- **Фонд как отдельный кошелёк** («перевести деньги в копилку»). Отклонено: issue #7 прямо требует резервирования без создания новых денег и без изменения суммы реальных балансов.
- **Хранить наступления плановых операций строками заранее.** Отклонено: бесконечные правила потребовали бы фонового досоздания и миграции строк при правке правила; отклонения хранятся точечно.
- **Плановые платежи кредита как `PlannedTransaction`.** Отклонено: два источника одного платежа — ровно тот двойной счёт, который запрещает #10.
