# API-контракты

Источники: [openapi.yaml](./openapi.yaml) (машиночитаемая спецификация, провалидирована `@redocly/cli lint` — 0 ошибок), [ddd-model.md](../architecture/ddd-model.md), [high-level-architecture.md](../architecture/high-level-architecture.md), [schema.md](../database/schema.md).

## Ресурсная модель

| Ресурс | Модуль | Соответствует |
|---|---|---|
| `/wallets` | Wallets | агрегат `Wallet` |
| `/wallet-types`, `/operation-types`, `/currencies` | ReferenceData | пользовательские справочники |
| `/operation-behavior-kinds` | ReferenceData | системный справочник (только чтение) |
| `/operations` | Operations | агрегат `Operation` |
| `/transfers` | Operations | агрегат `Transfer` |
| `/wallets/{id}/balance`, `/wallets/{id}/balance-history` | BalanceHistory | агрегат `BalanceSnapshot` |
| `/exchange-rates/*` | ExchangeRates | агрегат `ExchangeRateQuote` |
| `/reporting/total-amount` | Reporting | композиция без собственного агрегата |
| `/audit-entries` | Audit | агрегат `AuditEntry` |
| `/auth/login` | Host (сквозная забота) | не доменный ресурс |

Один REST-ресурс = один агрегат (кроме `/reporting/*`, которое намеренно нарушает это правило, так как Reporting — чисто читающая композиция, не агрегат — см. `ddd-model.md`). Переводы не смешаны с операциями в одном ресурсе: `POST /operations` создает только Income/Expense/Adjustment, для перевода — отдельный `POST /transfers`, отражающий, что перевод — самостоятельный агрегат, координирующий две операции атомарно (раздел 4 требований, `ddd-model.md` §2.5).

## Аутентификация

Решено на этапе высокоуровневой архитектуры: единый пароль без регистрации/ролей (см. `high-level-architecture.md` §8).

1. `POST /api/v1/auth/login { password }` → `{ token, expiresAt }` (JWT).
2. Все остальные эндпоинты требуют `Authorization: Bearer <token>` (схема `BearerAuth` в OpenAPI).
3. `429 Too Many Requests` на `/auth/login` — защита от подбора пароля (лимит попыток на уровне `Host`, деталь реализации).

## Соответствие HTTP-методов доменным командам

| HTTP | Использование | Пример |
|---|---|---|
| `GET` | Запрос, без побочных эффектов | `GET /wallets/{id}` |
| `POST /{collection}` | Команда создания агрегата | `POST /operations` → `CreateOperationCommand` |
| `POST /{resource}/{action}` | Именованная доменная команда, не являющаяся CRUD (нет более подходящего HTTP-метода) | `POST /wallets/{id}/archive` → `ArchiveWalletCommand`, `POST /wallets/{id}/set-primary` → `SetPrimaryWalletCommand` |
| `PATCH` | Частичное обновление изменяемых полей агрегата | `PATCH /operations/{id}` → `UpdateOperationCommand` |
| `PUT` | Полная замена одного конкретного поля с особым инвариантом | `PUT /wallets/{id}/currency` — выделено в отдельный эндпоинт, а не часть `PATCH`, так как имеет уникальное ограничение (запрет при наличии истории, Q15) |
| `DELETE` | Команда удаления, может быть отклонена (`409`), если сущность имеет историю | `DELETE /operations/{id}` |

Отдельные `POST .../archive`, `.../set-primary`, `.../deactivate`, `.../refresh` — осознанное отступление от чистого REST («никаких глаголов в URI» из общих рекомендаций) в пользу явного соответствия доменным командам из `ddd-model.md` §6: это не CRUD-операции над атрибутом, а именованные бизнес-операции со своими инвариантами (например, `set-primary` атомарно снимает флаг с прежнего основного кошелька) — сворачивать их в `PATCH { isPrimary: true }` скрыло бы это от читателя контракта.

## Пагинация

Единый курсорный формат для всех коллекций (`{ data: [...], pagination: { nextCursor, hasMore } }`), без исключений — даже для заведомо небольших списков (`wallet-types`, `currencies`), чтобы клиент Angular использовал один и тот же паттерн работы со списками везде. Курсор непрозрачен (opaque) — клиент не должен его парсить.

## Ошибки

Формат — RFC 7807 Problem Details (`application/problem+json`) везде. Основные коды:

| Код | Когда |
|---|---|
| `400` | Некорректное тело запроса (не проходит валидацию схемы) |
| `401` | Отсутствует/недействителен `Bearer`-токен |
| `404` | Сущность с указанным Id не найдена |
| `409` | Нарушение доменного инварианта (список — в описании конкретных ответов `openapi.yaml`, например: попытка удалить кошелек с историей, архивировать основной кошелек, перевод между разными валютами, удаление операции ≤ даты последнего слепка) |
| `429` | Только на `/auth/login` — превышен лимит попыток |
| `502` | Только `/exchange-rates/refresh` — Frankfurter недоступен (при этом возвращается 200 с последним известным курсом для планового автообновления; 502 — только когда пользователь явно запросил обновление и хочет знать, что оно не удалось) |

Rate limiting за пределами `/auth/login` не предусмотрен — однопользовательское приложение без публичного мультитенантного API, ограничивать по нагрузке нечего; это осознанное отступление от чек-листа skill'а `api-designer` («не забывай про rate limiting»), а не упущение.

## Версионирование

Префикс пути `/api/v1`. Следующая версия (если понадобится breaking change) — `/api/v2`, со временным сосуществованием обеих, пока Angular-клиент не перейдет на новую — детальная политика deprecation избыточна для внутреннего API с одним-единственным клиентом (собственный Angular SPA), но префикс версии заложен заранее, чтобы не переделывать все пути задним числом.
