# ADR-0010: Финансовое планирование — долги, фонды, бюджеты, плановые операции, прогноз

## Статус

**Принято (2026-11-14).** Ответы владельца на В1–В9 — раздел «Решения владельца». Детали п. 6 и п. 7, помеченные *предложение*, подтверждаются на ревью.

**Состояние реализации:** backend реализован полностью (п. 3–7), UI — в работе. Связанные суммы погашений и исполнений вычисляются из фактов операций (`IOperationFactsLookup`), подписки Debts и Planning на события Operations не понадобились. Открытые вопросы реализации — `docs/PROGRESS.md`, «Открытые вопросы v0.4.0».

## Контекст

Issues #5–#13 (v0.4.0) добавляют область, которую раздел 8 требований v1 явно исключал из первого этапа: бюджеты, регулярные платежи, долги, кредитные продукты, а раздел 1 — разделение фактического и доступного баланса. Тот же раздел 1 требовал не блокировать такое развитие архитектурно; текущая модель (модули с собственными схемами, связь по Id и событиям, [ADR-0001](./0001-modular-monolith.md)) это позволяет без изменения существующих агрегатов.

Сквозные требования из issues:

- **Нет двойного учёта.** Реальные деньги — только баланс `Wallet`, который меняют только фактические операции (`Operation`). Долг, фонд, бюджет и план деньги не создают и не списывают (#5, #6, #7, #9).
- **Связь с фактом.** Погашение долга и исполнение плана связываются с реальной операцией, а не дублируют её (#6, #8, #9).
- **Мультивалютность.** Где суммы разных валют сводятся вместе, явно показываются валюта расчёта, дата и источник курса (#10, #12).

## Решение

### 1. Различие понятий

| Понятие | Что это | Меняет баланс кошелька? |
|---|---|---|
| `Wallet` | Где лежат реальные деньги | Да — через операции |
| `Debt` (долг) | Сколько и кому вы должны; остаток и история погашений | Нет. Погашение — обычная операция расхода со ссылкой на долг |
| `Loan` (кредит) | Обязательство с графиком платежей | Нет. Платёж — обычная операция расхода со ссылкой на кредит |
| `Fund` (фонд) | Часть реальных денег кошельков, отложенная под цель | Нет. Резерв — пометка «эти деньги заняты» |
| `Budget` (бюджет) | Лимит расходов на месяц по категориям (`ExpenseCategory`) | Нет. Ничего не резервирует, только сравнивает факт с лимитом |
| `PlannedTransaction` (плановая операция) | Будущий доход или расход, разовый или повторяющийся | Нет, пока не исполнен. Исполнение создаёт обычную операцию |

### 2. Новые модули (bounded contexts)

По одному модулю и одной схеме БД на контекст (ADR-0001, ADR-0007): `Debts`, `Funds`, `Budgeting`, `Planning`. Модуль `Reporting` (read-only) расширяется прогнозом и свободными средствами. Новые агрегаты публикуют доменные события, Audit подписывается на них по общему механизму ([ADR-0006](./0006-audit.md)).

```
Debts      ──Id──▶ ReferenceData (Currency), Operations (OperationId платежа)   — агрегаты Debt и Loan
Funds      ──Id──▶ Wallets (WalletId резерва), Debts (необязательный DebtId/LoanId)
Budgeting  ──Id──▶ ReferenceData (OperationTypeId внутри ExpenseCategory, Currency)
Planning   ──Id──▶ ReferenceData (OperationTypeId, Currency), Wallets (WalletId), Operations (OperationId исполнения)
Operations ──событие──▶ Debts, Planning   (мягкое удаление/восстановление/изменение операции, на которую ссылается платёж или исполнение)
Funds      ──запрос──▶ Wallets            (текущий баланс кошелька при резервировании)
Budgeting  ──запрос──▶ Operations, ExchangeRates (фактические расходы за период, курсы)
Reporting  ──запрос──▶ Wallets, Funds, Debts, Planning, ExchangeRates (прогноз, свободные средства)
Debts, Funds, Budgeting, Planning ──событие──▶ Audit
```

### 3. Debts — долги и кредиты (#6, #8)

Долг и кредит — **две отдельные сущности** (В2). Проценты приложение не учитывает ни в каком виде (В5): суммы графика и платежей — это суммы к оплате, платёж целиком уменьшает остаток.

- **`Creditor`** — справочник кредиторов модуля (название; деактивация, если используется — по правилам [ADR-0002](./0002-record-lifecycle.md) §4). Общий для долгов и кредитов; число кредиторов не ограничено.
- **Агрегат `Debt`** (#6): `CreditorId`, название, валюта, исходная сумма, дата возникновения, статус (`Active`, `Repaid`, `Cancelled`). Остаток = исходная сумма − сумма учтённых погашений; при нуле статус становится `Repaid`. Внутри — **`DebtRepayment`**: `OperationId` фактического расхода и сумма (= сумма операции). Частичное и полное погашение, история погашений. Сводка: общий долг и разбивка по кредиторам (в валюте основного кошелька по последнему курсу, с датой курса).
- **Агрегат `Loan`** (#8): `CreditorId`, название, валюта, сумма к погашению, дата начала, статус (`Active`, `Repaid`, `Cancelled`). Внутри — **`LoanScheduleItem`** (дата, сумма; перенос даты и изменение условий — правка графика, график можно сгенерировать равными платежами) и **`LoanPayment`** (`OperationId`, сумма). Платёж сверяется с самыми ранними неоплаченными пунктами графика; статус пункта вычисляется: оплачен / частично / просрочен (дата < сегодня, не оплачен полностью) / ожидается. Видны ближайший платёж и остаток кредита.
- **Возникновение** (В3): долг, кредит и операция заводятся отдельно. Поступление денег, если нужно, — обычная операция дохода; Debts её не создаёт.
- **Погашение** (В4): пользователь в момент оплаты фиксирует обычный расход из кошелька в валюте долга/кредита, указав долг или кредит. Расход проходит через Operations как есть (баланс, история, «траты», аудит); Debts хранит только связь. Мягкое удаление операции → погашение перестаёт учитываться (событие `OperationDeleted`), восстановление — снова учитывается. Как деньги откладываются заранее — В9, п. 4.
- Задолженность, которую должны вам, в объём не входит (issues её не упоминают).

### 4. Funds — фонды и резервирование (#7)

- **Агрегат `Fund`**: название, целевая сумма, валюта (В6: одна валюта), необязательная ссылка на `Debt` или `Loan` (фонд на погашение), статус (`Active`, `Closed`).
- **`FundAllocation`** (сущность внутри `Fund`): `WalletId` + зарезервированная сумма. Резервировать можно из нескольких кошельков, все — в валюте фонда (В6). Резерв фонда = сумма аллокаций; прогресс = резерв / цель.
- **Проверка при создании резерва** (В7): новая или увеличенная аллокация не больше свободных средств кошелька = текущий баланс − резервы всех активных фондов по этому кошельку. Проверяет доменный сервис `ReservationPolicy` в транзакции команды (коллекционный инвариант, как `PrimaryWalletPolicy`). Так исключается двойное резервирование.
- **Расходы не блокируются** (В7). Если после операций баланс кошелька меньше его резервов, кошелёк и фонды показывают **дефицит обеспечения резерва** = резервы − баланс.
- Снятие резерва уменьшает аллокацию; закрытие фонда снимает все аллокации. Архивирование кошелька с резервом запрещено, пока резерв не снят.
- Сумма реальных балансов при резервировании не меняется — критерий #7 выполняется по построению.
- **Отложить деньги на долг и оплатить (В9).** Откладывание = резерв в фонде, связанном с долгом/кредитом; резерв уменьшает общую сумму, но тратой не является. Погашение, зафиксированное расходом из кошелька с резервом этого фонда, автоматически снимает резерв на сумму погашения (не больше аллокации кошелька), поэтому свободные средства не меняются второй раз. Мягкое удаление такого расхода возвращает снятый резерв (если свободных средств кошелька хватает; иначе резерв возвращается в пределах свободных средств).

### 5. Budgeting — месячные бюджеты (#11)

- **Справочник `ExpenseCategory`** (В1): название + набор типов операций с поведением `Expense`, которые в неё входят. Тип операции входит не более чем в одну категорию. Пользовательский справочник по правилам ADR-0002 §4 (деактивация, если используется в бюджете).
- **Агрегат `Budget`**: месяц (`YYYY-MM`), валюта; уникален на пару (месяц, валюта).
- **`CategoryLimit`** (сущность внутри `Budget`): `ExpenseCategoryId` + лимит.
- **Исполнение** (запрос): факт по категории = сумма не удалённых расходов типов этой категории с датой в месяце по всем кошелькам. Операции в другой валюте пересчитываются по историческому курсу на дату операции (В8), при отсутствии точного — последний известный на ту дату (как ADR-0004 §8). Остаток = лимит − факт; превышение — отрицательный остаток. Расходы вне категорий с лимитом показываются строкой «Без бюджета».
- **Перенос остатка** между месяцами не реализуется (В8).

### 6. Planning — плановые операции (#9)

- **Агрегат `PlannedTransaction`**: `OperationTypeId` (поведение `Income` или `Expense`), сумма, валюта, необязательный `WalletId` (в валюте плана), описание, дата первого наступления, необязательное `RecurrenceRule`, статус (`Active`, `Finished`).
- **`RecurrenceRule`** (VO): частота `Daily | Weekly | Monthly | Yearly`, интервал N, окончание — нет / до даты / после K повторов. Для `Monthly` число месяца; если в месяце его нет — последний день месяца. *(Предложение, бизнес-деталь — подтверждается на ревью.)*
- **Наступления** вычисляются из правила, не хранятся. Хранятся только отклонения — **`OccurrenceOverride`**: дата наступления + действие `Skip` (пропуск), `Move` (перенос на другую дату) или изменённая сумма.
- **`OccurrenceExecution`**: дата наступления + `OperationId` + исполненная сумма. Исполнение создаёт обычную операцию через Operations (форма предзаполнена из плана). Частичное исполнение: наступление остаётся ожидаемым на остаток, пока его не исполнят полностью или не пропустят *(предложение)*. Удаление операции исполнения (мягкое) возвращает наступление в ожидаемые.
- До исполнения план не влияет ни на баланс, ни на историю баланса.
- Плановые переводы в объём не входят (issue #9 говорит о доходах и расходах).

### 7. Reporting — прогноз и свободные средства (#10, #12)

- **`CashFlowForecast`** (read model, не хранится): по дням от сегодня до горизонта (по умолчанию 3 месяца, выбор 1/3/6/12 — *предложение*). Начальная точка — текущие балансы кошельков с признаком «в общей сумме». Движения: ожидаемые наступления плановых операций (с учётом пропусков, переносов, частичного исполнения) и неоплаченные платежи графиков кредитов. Результат: ожидаемый остаток на каждую дату, отмеченные отрицательные периоды, валюта расчёта = валюта основного кошелька.
- **Курсы в прогнозе:** последний известный курс; в ответе — дата курса и источник (Frankfurter). Будущее изменение курса не моделируется — это явное предположение, оно выводится в UI.
- **Без двойного счёта кредитного платежа:** единственный источник плановых платежей по кредиту — его график. Плановую операцию нельзя связать с кредитом; платёж по графику фиксируется как платёж кредита (п. 3). Просроченный неоплаченный платёж попадает в прогноз на сегодня.
- **Общая сумма** (В4, В9): резервы фондов уменьшают общую сумму — в сводке она равна свободным средствам кошельков «в общей сумме»; фактический баланс и резерв показываются рядом.
- **Свободные средства** (#12): по кошельку — фактический баланс, зарезервировано (аллокации фондов), свободно = факт − резерв. Сводка — то же в валюте основного кошелька с датой и источником курса. Ближайшие платежи (плановые расходы и платежи графиков на 30 дней) показываются отдельным списком и **не** вычитаются из свободных средств.

### 8. Жизненный цикл и аудит

- Долг с платежами, фонд с историей аллокаций, план с исполнениями физически не удаляются — переводятся в конечный статус (`Cancelled`, `Closed`, `Finished`). Без связанных данных — удаляются физически (по образцу ADR-0002).
- Все изменения пишутся в аудит через diff `ChangeTracker` (ADR-0006 §1). Аллокации, платежи, отклонения и исполнения — дочерние сущности: их изменения попадают в запись агрегата-владельца.
- Денежные суммы — произвольной точности, строками в API ([ADR-0005](./0005-money-precision.md)).

## Решения владельца (2026-11-14)

| № | Вопрос | Решение |
|---|---|---|
| В1 | Категория бюджета | Новый справочник категорий (`ExpenseCategory`), группирует типы операций |
| В2 | Долг и кредит | Две отдельные сущности (`Debt`, `Loan`) |
| В3 | Возникновение | Долг, кредит и операция заводятся отдельно |
| В4 | Погашение | Долг/кредит — отдельная сущность; деньги можно отложить заранее (общая сумма меньше, в тратах не видно), трата фиксируется в момент оплаты и появляется в тратах. Механизм откладывания — В9 |
| В5 | Проценты | Не учитываются вообще |
| В6 | Валюта фонда | Одна валюта; резерв из нескольких кошельков той же валюты |
| В7 | Баланс ниже резерва | Расходы не блокировать, показывать дефицит обеспечения резерва; при создании резерва проверять доступные средства |
| В8 | Бюджет | Пересчёт расходов по историческому курсу на дату операции; перенос остатка не реализуется |
| В9 | Как отложить деньги на долг | Резерв в фонде, связанном с долгом/кредитом; резерв уменьшает общую сумму; расход-погашение сам снимает резерв |

## Последствия

- Четыре новых модуля по структуре ADR-0007 и четыре новые схемы БД; существующие таблицы не меняются. Новая связь Operations → Debts/Planning только через события и Id.
- В Operations нужен контракт создания операции для исполнения плана и погашения долга (или UI создаёт операцию обычным API и передаёт `OperationId`) — выбирается при реализации, бизнес-правил не меняет.
- Прогноз и свободные средства считаются при запросе; для одного пользователя с сотнями плановых операций это дёшево, кэш не нужен.

## Отклонённые варианты

- **Фонд как отдельный кошелёк** («перевести деньги в копилку»). Отклонено: issue #7 прямо требует резервирования без создания новых денег и без изменения суммы реальных балансов.
- **Хранить наступления плановых операций строками заранее.** Отклонено: бесконечные правила потребовали бы фонового досоздания и миграции строк при правке правила; отклонения хранятся точечно.
- **Расчёт процентов по кредиту.** Отклонено владельцем (В5).
- **Категория бюджета = тип операции.** Отклонено владельцем (В1): нужен отдельный справочник.
- **Откладывание переводом в отдельный кошелёк.** Отклонено владельцем (В9).
- **Плановые платежи кредита как `PlannedTransaction`.** Отклонено: два источника одного платежа — ровно тот двойной счёт, который запрещает #10.
