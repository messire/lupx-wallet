# Пользовательские сценарии

Источник требований: [wallet_business_prompt_ru_v2.md](./wallet_business_prompt_ru_v2.md).

Документ описывает сценарии использования приложения личного учета финансов на первом этапе (единственный пользователь, без ролей и совместного доступа).

Обозначения:

- **Actor** — кто инициирует сценарий: `User` (пользователь) или `System` (фоновый процесс приложения).
- Пометка **⚠ Открытый вопрос Qn** означает, что точное поведение в требованиях не определено или противоречиво. Соответствующий вопрос см. в разделе «Открытые вопросы» и в чате с пользователем. До получения ответа сценарий не должен реализовываться на основании предположений.

## 1. Управление кошельками (Wallets)

### UC-01. Создание кошелька
- **Actor**: User
- **Предусловие**: нет.
- **Основной поток**: пользователь указывает название, валюту (выбирается из списка **доступных валют**, см. ниже), тип кошелька (из справочника типов), назначение/описание, начальный баланс, дату начала учета, признак включения в общую сумму, признак основного кошелька (опционально), порядок отображения, опционально цвет и иконку.
- **Результат**: создан новый кошелек с текущим балансом, равным начальному балансу; выбранная валюта, если она еще не активна, **автоматически становится активной** (добавляется в справочник валют пользователя); действие зафиксировано в аудите (создание кошелька и, если валюта была добавлена, создание валюты).
- **Решено ([ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7)**: список валют для выбора — это валюты, которые отдает сервис курсов (**доступные валюты**, названия английские); произвольный код и криптовалюты не принимаются. Если создание кошелька отклонено (например, не прошла проверка полей), валюта активной не становится.
- **Примечания**: наличие основного кошелька в системе обязательно (решено, Q7) — если это первый создаваемый кошелек, он автоматически становится основным. Пока список доступных валют не загружен из сервиса (свежая установка, сервис недоступен), создать кошелек нельзя: список загружается при старте приложения, при плановом и при ручном обновлении курсов (UC-08, UC-09).

### UC-02. Редактирование кошелька
- **Actor**: User
- **Основной поток**: пользователь изменяет название, тип, назначение, признак включения в общую сумму, порядок отображения, цвет/иконку и другие атрибуты существующего кошелька. Валюту можно изменить только у кошелька без операций (включая мягко удаленные).
- **Результат**: изменения сохранены, зафиксированы в аудите (значение до/после).
- **Решено (Q15, уточнено [ADR-0002](../architecture/adr/0002-record-lifecycle.md), 2026-09-30)**: смена валюты кошелька запрещена, если по нему есть хотя бы одна операция в прежней валюте, включая мягко удаленные (UC-14). Для кошелька без операций смена валюты допускается.
- **Выбор новой валюты** (выведено при реализации из [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7, отдельно с пользователем не обсуждалось): кошелек можно перевести только на **активную** валюту; чтобы использовать другую, пользователь сначала добавляет ее в активные (UC-28). Несуществующая валюта отклоняется.
- **Слепки при смене валюты**: слепки баланса историей не считаются (производные данные, рассчитанные системой) и смену валюты не блокируют. При смене валюты существующие слепки кошелька удаляются и перестраиваются в новой валюте (UC-23); оба действия фиксируются в аудите.
- **Курсы при смене валюты основного кошелька**: если меняется валюта основного кошелька, меняется и основная валюта приложения — курсы и история курсов к новой основной валюте загружаются так же, как при смене основного кошелька (UC-05, UC-08, UC-21). Выведено при реализации из [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §5 и §9.

### UC-03. Архивирование кошелька
- **Actor**: User
- **Основной поток**: пользователь архивирует кошелек вместо удаления. Архивирование — способ «убрать» кошелек, у которого есть операции (включая мягко удаленные): окончательно удалить такой кошелек нельзя (UC-04).
- **Результат**: кошелек помечен как архивный, остается доступным для просмотра истории, но не участвует в дальнейших операциях; его история и слепки баланса сохраняются; действие зафиксировано в аудите.
- **Решено (Q7)**: архивировать текущий основной кошелек запрещено — сначала пользователь должен назначить другой кошелек основным.
- **Решено (Q16)**: архивирование не изменяет автоматически признак «включен в общую сумму» — это независимые атрибуты. Если архивный кошелек не должен учитываться в общей сумме, пользователь обязан выключить флаг вручную.

### UC-04. Удаление кошелька (без истории операций)
- **Actor**: User
- **Основной поток**: пользователь удаляет кошелек, по которому не было операций.
- **Результат**: кошелек окончательно удален (физически, не архивирован); его слепки баланса удалены вместе с ним; в аудите зафиксированы удаление кошелька и удаление каждого слепка (со значением до удаления).
- **Решено (Q2, уточнено [ADR-0002](../architecture/adr/0002-record-lifecycle.md), 2026-09-30)**: кошелек без операций может быть удален окончательно. Кошелек, у которого есть хотя бы одна операция (включая мягко удаленные и обе стороны переводов), — только архивируется (см. UC-03).
- **Что считается историей кошелька**: только операции, введенные пользователем. Слепки баланса (создаются системой для всех кошельков) и ненулевой начальный баланс историей не считаются, поэтому пустой кошелек со слепками удаляется.
- **Ограничение**: основной кошелек нельзя ни удалить, ни архивировать, пока он основной (Q7).
- **Следствие**: удаление кошелька с ненулевым начальным балансом меняет историческую общую сумму за прошлые даты (UC-21).

### UC-05. Выбор основного кошелька
- **Actor**: User
- **Основной поток**: пользователь назначает один из существующих кошельков основным.
- **Результат**: прежний основной кошелек теряет признак; общая сумма начинает отображаться в валюте нового основного кошелька; действие зафиксировано в аудите.
- **Решено (Q8)**: основной кошелек всегда учитывается в общей сумме. Признак «включен в общую сумму» принудительно включается при назначении кошелька основным (и не может быть выключен, пока кошелек остается основным).

### UC-06. Изменение порядка отображения кошельков
- **Actor**: User
- **Основной поток**: пользователь вручную переупорядочивает список кошельков.
- **Результат**: новый порядок сохранен и используется при отображении списка.

### UC-07. Просмотр списка кошельков и их текущих балансов
- **Actor**: User
- **Основной поток**: пользователь открывает список кошельков (активных и, по отдельному запросу, архивных) и видит текущий баланс каждого в его собственной валюте.
- **Результат**: список отображен с учетом ручного порядка сортировки.

## 2. Курсы валют (Exchange rates)

### UC-08. Автоматическое обновление курсов
- **Actor**: System
- **Основной поток**: раз в сутки система запрашивает курсы валют из внешнего сервиса Frankfurter.
- **Результат при успехе**: новые курсы сохранены, зафиксированы дата и время обновления. В том же прогоне обновляется **список доступных валют** (UC-01, UC-28): новые валюты сервиса добавляются, названия обновляются, исчезнувшие из сервиса — убираются из доступных. Список обновляется и при отсутствии основного кошелька.
- **Результат при ошибке**: сохраняется последний успешно загруженный курс; таймер продолжает исходный суточный цикл. Если сервис не вернул список валют (ошибка, пустой или неразборчивый ответ), список доступных остается прежним.
- **Решено (Q5)**: источник курсов — сервис [Frankfurter](https://www.frankfurter.app/) (бесплатный, общедоступный, без ключа). ⚠ Изменение исходного требования: пользователь явно поменял периодичность автообновления с «раз в 3 часа» (раздел 2 исходного документа) на «раз в сутки» — это осознанное изменение бизнес-требования, а не молчаливое допущение (см. раздел «Изменения исходных требований» в конце файла).
- **Решено (Q6, уточнено пользователем 2026-09-16 и 2026-09-30, [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §4, §7)**: курсы запрашиваются напрямую как пара «активная валюта → текущая основная валюта» для всех **активных** валют (валют справочника пользователя), независимо от наличия кошельков, в том числе если валюта осталась только в архивных кошельках. Доступные, но не активные валюты не обновляются. Пара валюты с самой собой пропускается; без основного кошелька обновление курсов не выполняется. При смене основного кошелька (и, соответственно, основной валюты) курсы перезапрашиваются заново с новой базой, а история курсов (UC-21) загружается заново; промежуточная фиксированная базовая валюта не используется.
- **Валюта, которой нет в сервисе**: если сервис не поддерживает активную валюту (например, она осталась от прежних данных), ее курс пропускается без ошибки, а сама валюта остается активной с последним известным курсом. Если сервис перестал отдавать валюту, она исчезает из доступных, но остается активной (§6 ADR-0004). Выведено при реализации, отдельно с пользователем не обсуждалось.
- **Актуальность списка валют**: названия валют — английские, из сервиса; при обновлении списка названия активных валют приводятся к названиям сервиса, изменение фиксируется в аудите (UC-25).

### UC-09. Ручное обновление курсов
- **Actor**: User
- **Основной поток**: пользователь нажимает кнопку обновления курсов; система запрашивает курсы всех **активных** валют к валюте основного кошелька по тем же правилам, что в UC-08, и обновляет список доступных валют. Кнопка доступна и без основного кошелька — в этом случае обновляется только список доступных валют.
- **Результат при успехе**: курсы и список доступных валют обновлены, суточный таймер автообновления запускается заново от момента ручного обновления.
- **Результат при ошибке**: используется последний успешно загруженный курс; список доступных остается прежним; таймер также перезапускается. Ошибка пары или списка валют сообщается пользователю как недоступность источника.
- **Примечание**: ручное обновление не ждет загрузки истории курсов (UC-21), но запускает ее: после ручного обновления (успешного или нет) система в фоне дозагружает историю курсов недостающих валют и дат и заново отсчитывает сутки до планового прогона.

### UC-10. Просмотр времени последнего обновления курсов
- **Actor**: User
- **Основной поток**: пользователь видит дату и время последнего *успешного* обновления курсов.
- **Результат**: отображена метка времени последнего успешного обновления.

## 3. Операции (Operations)

### UC-11. Регистрация операции дохода
- **Actor**: User
- **Основной поток**: пользователь создает операцию с типом, ссылающимся на справочник типов операций, относящуюся к базовому поведению «доход»; указывает кошелек, сумму, дату.
- **Результат**: баланс кошелька увеличен; операция зафиксирована в аудите.
- **Примечания**: тип операции может по смыслу совпадать с категорией (см. UC-15, решение по Q1), но не используется для аналитики на этом этапе.

### UC-12. Регистрация операции расхода
- **Actor**: User
- **Основной поток**: аналогично UC-11, но базовое поведение «расход» — баланс кошелька уменьшается.

### UC-13. Редактирование операции
- **Actor**: User
- **Основной поток**: пользователь изменяет сумму, дату, тип, кошелек или иные атрибуты ранее созданной операции, в том числе датированной прошедшим числом.
- **Результат**: изменение сохранено; в аудите зафиксированы значения до и после; система пересчитывает слепки баланса за дату операции и за все последующие даты (см. UC-23).
- **Решено (Q4)**: пересчет каскадный — распространяется на все слепки после даты измененной операции, чтобы накопительная история оставалась корректной.
- **Ограничение**: мягко удаленную операцию редактировать нельзя — сначала ее нужно восстановить (UC-14). Операцию, являющуюся частью перевода, редактировать отдельно нельзя — только через перевод целиком (UC-16).

### UC-14. Удаление и восстановление операции
- **Actor**: User
- **Основной поток (удаление)**: пользователь удаляет ранее созданную операцию, не связанную с переводом (см. UC-16), с любой датой, включая сегодняшнюю.
- **Результат**: удаление **мягкое** — запись физически не стирается. Операция остается в списке операций и отображается серой, перечеркнутой красной линией; не участвует в расчете текущего баланса кошелька, слепков баланса и общей суммы; система пересчитывает слепки баланса за дату операции и за все последующие даты (UC-23); в аудите зафиксировано удаление со значением записи до изменения.
- **Альтернативный поток (восстановление)**: пользователь восстанавливает мягко удаленную операцию. Она снова участвует в расчетах, слепки баланса пересчитываются от даты операции (UC-23), восстановление фиксируется в аудите. Восстановление возможно всегда: повторная проверка даты, типа операции или состояния кошелька не выполняется.
- **Ограничения**:
  - мягко удаленную операцию нельзя редактировать, пока она не восстановлена (UC-13);
  - повторное удаление уже удаленной операции и восстановление не удаленной — отклоняются;
  - операцию, являющуюся частью перевода, удалять и восстанавливать отдельно нельзя — только через перевод целиком (UC-16);
  - физического удаления операций нет: кошелек, у которого была хотя бы одна операция (в том числе удаленная), окончательно удалить нельзя (UC-04).
- **Решено (Q2, уточнено пользователем 2026-09-30, [ADR-0002](../architecture/adr/0002-record-lifecycle.md))**: операции удаляются только мягко, с любой датой, и могут быть восстановлены. Прежнее физическое удаление с ограничениями по дате отменено: ошибочные операции задним числом должны быть исправимы.
- **Корректирующая сумма** ([ADR-0003](../architecture/adr/0003-balance-history.md), §6) мягкому удалению не подлежит; правило вступает в силу вместе с заявленным балансом.

### UC-15. Добавление нового типа операции пользователем
- **Actor**: User
- **Основной поток**: пользователь добавляет новый элемент в справочник типов операций (например, «зарплата», «продукты»), если новый тип укладывается в уже поддерживаемое поведение (доход/расход/перевод/корректировка).
- **Результат**: новый тип операции доступен для выбора при создании операций.
- **Решено (Q1)**: типы операций могут выполнять роль категорий (пользователь свободно добавляет «зарплата», «продукты», «кэшбэк» и т.п.), но на первом этапе по ним **не строится аналитика и отчетность** (никаких сумм/графиков в разрезе категории-типа) — это остается ограничением раздела 8.

## 4. Переводы (Transfers)

### UC-16. Перевод между кошельками одной валюты
- **Actor**: User
- **Предусловие**: исходный и целевой кошельки имеют одинаковую валюту.
- **Основной поток**: пользователь указывает исходный кошелек, целевой кошелек и сумму; создаются две связанные операции — списание и зачисление.
- **Результат**: обе операции применяются как единое действие; балансы обоих кошельков обновлены; в аудите зафиксировано перевод целиком, включая связь между двумя операциями.
- **Альтернативный поток (удаление перевода)**: пользователь удаляет перевод — **мягко**, с любой датой, обе операции («ноги») вместе, как единое действие. Перевод и обе его операции остаются в списках и отображаются серыми, перечеркнутыми красной линией; не участвуют в расчете баланса, слепков и общей суммы ни одного из двух кошельков; слепки обоих кошельков пересчитываются (UC-23); удаление фиксируется в аудите.
- **Альтернативный поток (восстановление перевода)**: пользователь восстанавливает мягко удаленный перевод — обе операции возвращаются в расчеты одновременно, слепки обоих кошельков пересчитываются, восстановление фиксируется в аудите.
- **Ограничения**: отдельную «ногу» перевода нельзя удалить, восстановить или отредактировать через операции — только через перевод целиком; повторное удаление удаленного перевода и восстановление не удаленного — отклоняются. Удаление перевода — только мягкое ([ADR-0002](../architecture/adr/0002-record-lifecycle.md), §3).
- **Решено (Q10)**: сумма списания всегда равна сумме зачисления — комиссия за перевод между своими кошельками не поддерживается. Тип операции «комиссия» (пример из раздела 3) — это отдельный, не связанный с переводом расход (например, комиссия банка за обслуживание счета), создаваемый как обычная операция расхода (UC-12).

### UC-17. Попытка перевода между кошельками разных валют
- **Actor**: User
- **Основной поток**: пользователь пытается создать перевод между кошельками с разными валютами.
- **Результат**: операция запрещена правилами раздела 4 требований.
- **Решено (Q9)**: конвертация валют при переводе на первом этапе не предусмотрена вообще; для перемещения денег между кошельками разных валют пользователь вручную создает две несвязанные операции (расход в одном кошельке, доход в другом).

## 5. Баланс и история (Balance)

### UC-18. Просмотр текущего баланса кошелька
- **Actor**: User
- **Результат**: отображен актуальный баланс кошелька в его валюте. Мягко удаленные операции и переводы в балансе не учитываются (UC-14).

### UC-19. Просмотр общей суммы по всем кошелькам
- **Actor**: User
- **Основной поток**: система суммирует балансы кошельков с включенным признаком «включен в общую сумму», конвертируя их в валюту текущего основного кошелька по актуальному курсу.
- **Результат**: отображена общая сумма.
- **Примечания**: основной кошелек всегда включен в сумму (решено, Q8); наличие основного кошелька гарантировано (решено, Q7), поэтому сумма никогда не может быть «без основы».

### UC-20. Просмотр баланса кошелька на выбранную дату
- **Actor**: User
- **Основной поток**: пользователь выбирает дату; система показывает баланс кошелька на эту дату на основании слепка истории баланса.
- **Результат**: отображен исторический баланс.
- **Решено (Q13)**: для даты раньше «даты начала учета» кошелька баланс считается равным 0.

### UC-21. Просмотр исторической общей суммы на дату
- **Actor**: User
- **Основной поток**: система суммирует исторические балансы кошельков (по слепкам) на выбранную дату, конвертируя их в валюту *текущего* основного кошелька по курсу, актуальному на эту дату (либо последнему известному курсу до этой даты, если точного курса на дату нет, например в выходной).
- **Результат**: отображена историческая общая сумма и всегда — строка «Курс по состоянию на <дата>» с датой курсов, фактически примененных при расчете (самая ранняя из них, если курсы разных валют взяты на разные даты); дата показывается и тогда, когда совпадает с выбранной.
- **Решено ([ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §8, §9)**: расчет использует **только данные приложения**: курсы читаются из базы, к внешнему сервису в момент просмотра приложение не обращается (ни для текущей, ни для исторической суммы). Историю курсов система загружает заранее, в фоне: когда валюта становится активной, при создании кошелька, при смене валюты кошелька и основного кошелька (и, соответственно, основной валюты), при старте, по расписанию и после ручного обновления курсов (UC-09) — за период от самой ранней даты начала учета до сегодняшнего дня.
- **Неполная сумма**: пока загрузка истории не завершена (после добавления валюты, смены основной валюты, первого запуска), кошельки, для которых на выбранную дату нет курса, **исключаются** из суммы с указанием причины; сумма за такие даты неполная. В причине указан код валюты кошелька и дата («Курс валюты EUR на дату 2026-05-01 недоступен.»). Экран показывает число не учтенных кошельков, список «кошелек — причина» и подпись «Сумма неполная: история курсов ещё загружается, повторите позже». После завершения загрузки тот же запрос возвращает полную сумму.
- **Период истории** (выведено при реализации из ADR-0004, §9, отдельно с пользователем не обсуждалось):
  - самая ранняя дата начала учета берется среди **всех** кошельков, включая архивные, поэтому создание кошелька с более ранней датой начала учета расширяет историю курсов всех активных валют;
  - историю система ежедневно продлевает до сегодняшнего дня, иначе правило «ближайший более ранний курс» молча подставляло бы устаревший курс;
  - если у сервиса нет курсов за часть периода (валюта появилась в данных позже начала периода или ее данные закончились раньше), загружается то, что есть; для дат раньше начала данных валюты курса нет, и кошелек в такой валюте исключается из суммы с указанием причины.

### UC-22. Автоматическое создание/обновление дневного слепка баланса
- **Actor**: System
- **Основной поток**: ежедневно в 12:00 UTC система создает или обновляет по одной записи слепка баланса на каждый кошелек на текущую дату.
- **Результат**: слепок баланса создан/обновлен; действие зафиксировано в аудите.
- **Решено (Q12)**: если приложение не работало в момент 12:00 UTC, пропущенные слепки досоздаются задним числом (при следующем запуске приложения система обнаруживает пропущенные даты и досоздает слепки за них).

### UC-23. Каскадный пересчет слепков баланса при ретроактивном изменении
- **Actor**: System (инициируется действием пользователя)
- **Основной поток**: пользователь вносит ручную корректировку баланса или изменяет, мягко удаляет либо восстанавливает операцию (или перевод), влияющую на баланс за прошедшую дату; система обновляет слепок за эту дату и последовательно пересчитывает все слепки за все последующие даты вплоть до сегодняшней.
- **Результат**: вся накопительная история баланса кошелька после затронутой даты остается корректной; каждое обновление слепка зафиксировано в аудите.
- **Решено (Q4)**: пересчет каскадный (все последующие даты), а не только слепок затронутой даты.
- **Удаление и восстановление** ([ADR-0002](../architecture/adr/0002-record-lifecycle.md), §3): мягко удаленная запись в пересчете не участвует, восстановленная — участвует снова; запись, удаленная или восстановленная с любой датой (включая сегодняшнюю), запускает пересчет от своей даты. Для перевода пересчитываются оба кошелька независимо.
- **Удаление и смена валюты кошелька** (UC-04, UC-02): слепки кошелька — производные данные; при удалении кошелька они удаляются вместе с ним, при смене валюты — удаляются и перестраиваются от даты начала учета в новой валюте.

### UC-24. Ручная корректировка баланса
- **Actor**: User
- **Основной поток**: пользователь выбирает способ ввода корректировки — либо задает новое абсолютное значение баланса кошелька на дату, либо задает дельту изменения (+/-); система применяет корректировку соответствующим способом.
- **Результат**: баланс кошелька изменен; операция корректировки, выбранный способ ввода (абсолютное значение/дельта) и её влияние на слепок баланса зафиксированы в аудите.
- **Решено (Q3)**: поддерживаются оба способа ввода корректировки, пользователь выбирает нужный при создании корректировки.

## 6. Аудит (Audit)

### UC-25. Просмотр истории изменений записи
- **Actor**: User
- **Основной поток**: пользователь открывает историю аудита для конкретной записи (кошелек, операция, перевод, слепок баланса).
- **Результат**: отображен список изменений с указанием: что изменилось, когда, какая запись затронута, значение до, значение после, кто внес изменение (пользователь или система).
- **Примечания**: история аудита не должна теряться при последующих изменениях данных (append-only по духу требований).

## 7. Справочники (Reference dictionaries)

### UC-26. Просмотр справочника типов кошельков
- **Actor**: User

### UC-27. Просмотр справочника типов операций
- **Actor**: User

### UC-28. Добавление элемента справочника (тип кошелька / тип операции / валюта)
- **Actor**: User
- **Основной поток (тип кошелька, тип операции)**: пользователь добавляет новый элемент справочника, если он укладывается в уже поддерживаемое поведение системы.
- **Основной поток (валюта)**: пользователь добавляет валюту **в активные** — выбирает ее из списка доступных валют (UC-01; список ведет система по данным сервиса курсов, пользователь им не управляет). Название берется из списка доступных (английское). Произвольный код, криптовалюта и любой код, которого нет среди доступных, отклоняются; уже активная валюта повторно не добавляется. После добавления система в фоне загружает курсы валюты и ее историю (UC-08, UC-21). Валюта также становится активной автоматически при создании кошелька в ней (UC-01).
- **Решено (Q11, уточнено [ADR-0002](../architecture/adr/0002-record-lifecycle.md), §4, [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7)**: тип кошелька или тип операции, уже используемый существующими записями, нельзя удалить — только деактивировать (скрыть из выбора для новых записей), по аналогии с архивированием кошельков; неиспользуемый удаляется окончательно. **У валюты состояния «деактивирована» нет**: валюта либо активна, либо нет; ее можно «убрать из активных» (удалить из справочника валют пользователя) только если она не используется.
- **Что считается использованием элемента**: ссылки от кошельков (включая архивные) и от операций, **включая мягко удаленные** — чтобы восстановление операции всегда было возможно. Записи курсов валют использованием валюты не считаются.
- **Валюта**: используется, если на нее ссылается кошелек или операция (включая удаленную). Используемую валюту убрать из активных нельзя (отказ с пояснением, что валюта используется кошельком или операцией, включая удаленные). Неиспользуемая валюта убирается окончательно; ее курсы (последние и исторические) и сведения о загруженной истории удаляются вместе с ней. Убранная валюта остается среди доступных и может быть добавлена снова.
- `OperationBehaviorKind` — системный справочник, пользователю недоступен и этому правилу не подчиняется.

## 8. Явно вне рамок первого этапа

Согласно разделу 8 исходных требований, следующие сценарии **не реализуются** на первом этапе (перечислены для полноты картины и трассируемости, без описания потока):

- сложная аналитика и отчетность по категориям/типам операций (решено по Q1: сами типы-категории добавлять можно, см. UC-15, но отчетности по ним на этом этапе нет);
- бюджеты;
- регулярные платежи;
- долги;
- кредитные продукты;
- импорт банковских выписок;
- совместный доступ, роли и права;
- синхронизация между несколькими пользователями;
- разделение фактического и доступного баланса, кредитные лимиты и задолженность (при этом архитектура не должна блокировать их добавление в будущем).

## Открытые вопросы, влияющие на сценарии

Все вопросы Q1–Q16, поднятые при анализе исходных требований, решены пользователем; решения отражены в соответствующих сценариях выше пометкой «Решено (Qn)». Пометок ⚠ без решения в этом документе больше не осталось. Итоговый свод решений — см. таблицу ниже.

| № | Вопрос (кратко) | Решение |
|---|---|---|
| Q1 | Тип операции vs категория | Тип операции выполняет роль категории; отчетности/аналитики по типам на первом этапе нет |
| Q2 | Удаление кошельков/операций | Кошелек без операций удаляется окончательно, с операциями (включая удаленные) — только архивирование; операции и переводы удаляются только мягко (с любой датой, с восстановлением) — уточнено [ADR-0002](../architecture/adr/0002-record-lifecycle.md), 2026-09-30 |
| Q3 | Способ ручной корректировки | Поддерживаются оба способа: абсолютное значение и дельта — выбирает пользователь |
| Q4 | Каскадный пересчет истории | Пересчитываются все слепки баланса после затронутой даты |
| Q5 | Источник курсов валют | Сервис Frankfurter; периодичность автообновления изменена с 3 часов на 1 сутки (см. «Изменения исходных требований») |
| Q6 | Модель кросс-курсов | Прямой запрос пары «активная валюта → текущая основная валюта» только для активных валют (доступные, но не активные не обновляются); наличие кошелька не требуется; при смене основного кошелька курсы и история курсов перезагружаются с новой базой (уточнение пользователя 2026-09-16; «только активные» — 2026-09-30, [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §4, §7, §9) |
| Q7 | Обязательность основного кошелька | Основной кошелек обязателен всегда; архивировать текущий основной нельзя |
| Q8 | Основной кошелек и общая сумма | Основной кошелек всегда включен в общую сумму, флаг принудительно включен |
| Q9 | Кросс-валютные переводы | Не поддерживаются; пользователь делает две несвязанные операции вручную |
| Q10 | Тип операции «комиссия» | Обычный расход, не связанный с переводом; комиссия за перевод между своими кошельками не предусмотрена |
| Q11 | Изменение элементов справочника | Используемый тип кошелька или тип операции (ссылки от кошельков и операций, включая удаленные) можно только деактивировать, не удалять. У валюты деактивации нет: валюта активна или нет; используемую валюту убрать из активных нельзя, курсы использованием не считаются и удаляются вместе с валютой ([ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7) |
| Q12 | Пропущенный ежедневный снепшот | Досоздается задним числом при следующем запуске приложения |
| Q13 | Баланс до даты начала учета | Равен 0 |
| Q14 | Точность денежных сумм | Произвольная точность (не только 2 знака). Обоснование «для поддержки криптовалют» утратило силу: криптовалюты не поддерживаются, список валют ограничен сервисом курсов ([ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7); решение о точности не меняется ([ADR-0005](../architecture/adr/0005-money-precision.md)) |
| Q15 | Смена валюты кошелька | Запрещена при наличии операций (включая удаленные); допустима для кошелька без операций, слепки перестраиваются в новой валюте |
| Q16 | Архивирование и флаг «включен в общую сумму» | Независимые атрибуты; архивирование не меняет флаг автоматически |
