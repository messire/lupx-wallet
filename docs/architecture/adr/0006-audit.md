# ADR-0006: Аудит — захват изменений, актор, метки времени, объём журнала

## Статус

Принято (2026-09-11). Пересобрано 2026-09-30.

**Состояние реализации:** реализовано. Известные упрощения — в разделе «Состояние реализации».

## Контекст

Раздел 6 требований: каждое изменение данных отслеживается, история аудита не должна теряться. [ddd-model.md](../ddd-model.md) (§2.8, §5) и `docs/database/schema.md` (`audit.audit_entries.changes jsonb`) требуют в каждой записи значения полей **до и после**, а не только факт изменения. Доменные события модулей несут только идентификаторы — они спроектированы под нужды истории баланса, которой диффы не требовались.

## Решение

### 1. Базовый механизм — diff из EF Core `ChangeTracker`

`DispatchDomainEventsInterceptor` ([ADR-0001](./0001-modular-monolith.md), §5) в `SavingChangesAsync`, пока `OriginalValues` и `CurrentValues` ещё различаются, для каждого агрегата с неопубликованными событиями вычисляет список `EntityFieldChange(FieldName, OldValue, NewValue)` по собственным свойствам (не навигационным и не ключевым):

- `Added` → все поля из `null` в текущее значение;
- `Deleted` → полный снимок из исходных значений в `null`;
- `Modified` → только изменённые свойства.

Результат хранится в словаре по `IDomainEvent.EventId`; один diff присваивается каждому событию агрегата за один `SaveChanges`. Подписчик Audit забирает его при диспетчеризации методом `TakeChanges(eventId)`, который удаляет запись из словаря — словарь не растёт сверх числа ещё не обработанных событий. Отдельный интерцептор для аудита не заводится: он дважды проходил бы тот же `ChangeTracker` в том же хуке.

`Audit.Infrastructure` ссылается на `Domain` пяти модулей-издателей ради типов событий (ADR-0001, способ e). `EntityFieldChange` живёт в `BuildingBlocks.Infrastructure` и не зависит от Audit.

### 2. Точечное обогащение

Где diff из `ChangeTracker` бессмыслен, обработчик формирует `changes` из полей события (`AuditRecorder.RecordAsync` вместо `RecordFromChangeTrackerAsync`):

- **`BalanceSnapshotCreated`/`BalanceSnapshotUpdated`.** `SnapshotDate` — часть составного ключа и исключается из diff; без неё записи разных дат одного кошелька были бы неотличимы. В `changes` кладутся `SnapshotDate` и `Balance`; `entity_id` — `WalletId`.
- **`ExchangeRatesUpdated`/`ExchangeRateUpdateFailed`.** События батчевые, описывают прогон целиком. `changes` — список пар с новым курсом или причиной отказа; `entity_id` — `Guid.Empty`, поскольку единственной строки-владельца нет, а схема требует непустое значение.

Новые события с составным ключом без суррогата или батчевые решаются по аналогии явно, а не молча через общий механизм.

### 3. Монотонные метки времени

`GET /audit-entries` сортирует по `occurred_at DESC` с курсором по этому же полю. Второго уникального поля для устранения неоднозначности нет (`Id` не транслируется EF Core в сравнение), а `occurred_at` может совпасть у записей одной транзакции — каскадный пересчёт создаёт много записей быстрее разрешения часов. `AuditEntry.Create` берёт время из `MonotonicClock.UtcNow()` (`Audit.Domain`): строго возрастающие метки в пределах процесса, при коллизии — предыдущий тик + 1. Сдвиг от реального времени — доли микросекунды; зато курсор из одного поля не даёт дублей и пропусков.

### 4. Объём журнала при каскадном пересчёте

`ddd-model.md` §6 требует по одной записи на каждый обновлённый слепок — это бизнес-требование, не техническая деталь. Решение — оставить: одна `AuditEntry` на каждое событие слепка, в той же транзакции, что и пересчёт. Смягчение — только на уровне реализации (словарь диффов очищается по мере чтения, одна вставка на событие). Переход к агрегированной записи на прогон потребовал бы изменения бизнес-требования и явного запроса пользователя.

### Механизм актора (User/System)

`IAuditActorAccessor` (`BuildingBlocks.Infrastructure`, Scoped): по умолчанию `User`. ASP.NET Core создаёт scope на каждый запрос, поэтому пользовательские команды помечены `User` без дополнительного middleware; каскадный пересчёт, вызванный синхронно из запроса, наследует `User`. Фоновые сервисы (`BalanceSnapshotSchedulerHostedService`, `ExchangeRateRefreshBackgroundService`) первым действием в своём scope вызывают `SetSystemActor(<имя сервиса>)`. Абстракция живёт в `BuildingBlocks.Infrastructure`, а не в `Audit.Application`: её пишут фоновые сервисы других модулей, которые не должны ссылаться на Audit.

### Что фиксируется

Создание, изменение, физическое удаление, архивирование, деактивацию, мягкое удаление и восстановление любой записи; каждый созданный или обновлённый слепок; каждое изменение корректирующей суммы ([ADR-0003](./0003-balance-history.md), §6); результат каждого прогона обновления курсов. Журнал неизменяем: `CREATE RULE ... DO INSTEAD NOTHING` на `UPDATE`/`DELETE`.

### Тестовая инфраструктура: `audit.audit_entries` и Respawn

`DELETE`, который генерирует Respawn, из-за `CREATE RULE` становится безрезультатным no-op без ошибки — данные аудита копились бы между тестами молча. Схема `audit` исключена из `RespawnerOptions.SchemasToInclude`; `ApiTestFixture.ResetAsync()` дополнительно выполняет `TRUNCATE TABLE audit.audit_entries` — `TRUNCATE` правилами не перехватывается.

## Последствия

- Механизм захвата не требует правок `Domain` ни одного модуля-издателя.
- Актор фоновых задач определяется местом вызова, а не типом команды: одна и та же команда из запроса даёт `User`, из фонового сервиса — `System`.
- Монотонные часы — на процесс; вместе с сигналами в памяти это часть ограничения «один экземпляр backend» (ADR-0001, §8).

## Состояние реализации

- Аудит обновления курсов пишется после сохранения курсов, вне общей транзакции (следствие `RefreshExchangeRatesCommand` вне `ICommand`).
- В `changes` для курсов валюты представлены `CurrencyId`, а не кодами.
- Имена полей, отображённых через shadow-свойства EF (например, `_initialBalanceAmount`), попадают в `changes` как внутренние имена, а не доменные.
- Мягкое удаление, восстановление и корректирующая сумма появятся вместе с ADR-0002 и ADR-0003.

## Отклонённые варианты

- **Обогатить доменные события полями old/new** — правки `Domain` пяти модулей ради одного подписчика.
- **Чистый ChangeTracker-diff без исключений** — не работает для составного ключа `BalanceSnapshot` и батчевых событий курсов.
- **Отдельный интерцептор для аудита** — дублирует итерацию `ChangeTracker`.
- **Тиебрейкер курсора по `Id`** — типизированный Id не транслируется в SQL-сравнение.
- **Агрегированная запись аудита на прогон пересчёта** — меняет бизнес-требование.
