# ADR-0012: Структура репозитория и конвенции размещения файлов

## Статус

Принято — 2026-09-12. Реализация начинается по плану в [docs/PROGRESS.md](../../PROGRESS.md#план-структурный-рефакторинг-2026-09-12).

## Контекст

Пользователю трудно ориентироваться в коде. Первый этап рефакторинга должен сделать размещение файлов предсказуемым, сохранив поведение приложения.

По результатам просмотра репозитория:

- Backend содержит 30 проектов; пути повторяют имя модуля, например `Modules/Wallets/Wallets.Application/LupexWallet.Wallets.Application.csproj`.
- В корнях слоёв смешаны сценарии, интерфейсы, политики, работа с БД, межмодульные адаптеры и регистрация зависимостей.
- Frontend уже разделён на features, но страницы импортируют HTTP-сервисы и модели из соседних features.
- Название `operations.service.ts` не уточняет, что это HTTP-клиент.
- Комментарии местами содержат историю этапов и исправлений вместо объяснения текущего устройства.

Контекст размещения, выбранный пользователем: один GitHub-репозиторий, Angular на Vercel, .NET API и PostgreSQL на Railway с приватным соединением между API и БД. Supabase не используется. Настройка облачных сервисов не входит в этот структурный рефакторинг.

## Предлагаемое решение

### 1. Явные границы backend и frontend

│   │   │   ├── Wallets/
│   │   │   ├── Operations/

│   │   │   ├── BalanceHistory/
│   │   │   ├── ExchangeRates/
│   │   │   ├── Reporting/
│   │   │   └── Audit/
│   │   └── BuildingBlocks/
│   │       ├── SharedKernel/
│   │       └── Infrastructure/
│   ├── tests/
│   │   ├── LupexWallet.UnitTests/
│   │   └── LupexWallet.IntegrationTests/
│   ├── LupexWallet.sln
│   ├── Directory.Build.props
│   ├── Directory.Packages.props

Дерево показывает целевое размещение, а не утверждает наличие всех файлов сегодня. Dockerfile и workflow-файлы создаются в рамках настройки сборки/деплоя, если отсутствуют; сама публикация приложения сюда не входит.

Backend и frontend имеют собственные инструкции запуска и настройки сборки. Корневой README — короткая точка входа со ссылками. `docker-compose.yml` остаётся в корне для локального окружения. Документация описывает фактическое состояние; предложенное дерево не подменяет его до переноса.

### 2. Единый шаблон backend-модуля

```text
Modules/Wallets/
├── Domain/
│   ├── LupexWallet.Wallets.Domain.csproj
│   ├── Wallet.cs
│   ├── Events/
│   └── Exceptions/
├── Application/
│   ├── LupexWallet.Wallets.Application.csproj
│   ├── UseCases/
│   │   ├── CreateWallet/
│   │   │   └── CreateWalletCommand.cs
│   │   ├── UpdateWallet/
│   │   ├── ArchiveWallet/
│   │   ├── GetWallet/
│   │   └── ListWallets/
│   ├── Abstractions/
│   │   ├── Persistence/
│   │   └── Integration/
│   ├── Models/
│   └── Policies/
├── Infrastructure/
│   ├── LupexWallet.Wallets.Infrastructure.csproj
│   ├── Persistence/
│   │   ├── WalletsDbContext.cs
│   │   ├── Configurations/
│   │   ├── Repositories/
│   │   └── Migrations/
│   ├── Integration/
│   └── WalletsModuleExtensions.cs
└── Api/
    ├── LupexWallet.Wallets.Api.csproj
    ├── Contracts/
    └── Endpoints/
```

Полные имена проектов и сборок сохраняются; названия папок слоёв сокращаются. Пример UseCases не является исчерпывающим списком действий: все существующие сценарии сохраняются.

| Назначение | Расположение внутри модуля |
|---|---|
| Пользовательский сценарий | `Application/UseCases/<Action>/` |
| Правила сущности | `Domain/` |
| Интерфейсы хранения | `Application/Abstractions/Persistence/` |
| Интерфейсы взаимодействия модулей | `Application/Abstractions/Integration/` |
| Общие для сценариев модели и политики | `Application/Models/`, `Application/Policies/` |
| EF Core, репозитории, миграции | `Infrastructure/Persistence/` |
| Межмодульные адаптеры | `Infrastructure/Integration/` |
| Фоновые задачи | `Infrastructure/BackgroundJobs/` |
| Внешние HTTP-клиенты | `Infrastructure/ExternalServices/` |
| HTTP-маршруты и контракты | `Api/Endpoints/`, `Api/Contracts/` |

Пустые папки ради шаблона не создаются. У Reporting не появляется Domain ради симметрии. Команда и её обработчик могут остаться в одном файле внутри папки сценария. Разделение существующих крупных файлов — отдельный этап работы с кодом.

Перемещение интерфейсов не меняет их владельца и направление зависимостей. Сохраняются действующие межмодульные правила и исключения ADR-0006…ADR-0011, включая consumer-owned порты и подписки на доменные события.

### 3. Frontend: экраны отдельно от доступа к данным

```text
frontend/src/app/
├── core/
│   ├── auth/
│   └── http/
├── data-access/
│   ├── wallets/
│   │   ├── wallets-api.service.ts
│   │   └── wallets-api.models.ts
│   ├── operations/
│   ├── transfers/
│   ├── reference-data/
│   └── ...
├── features/
│   ├── wallets/
│   │   └── pages/
│   │       └── wallets-page/
│   ├── operations/
│   │   ├── pages/
│   │   │   └── operations-page/
│   │   └── components/
│   │       └── operation-form/
│   └── ...
├── shared/
│   ├── ui/
│   ├── money/
│   └── pagination/
├── layout/
│   └── shell/
├── app.routes.ts
└── app.config.ts
```

- `pages` — компоненты, открываемые по маршруту; `components` — компоненты конкретной feature.
- `data-access` — HTTP-клиенты и модели API по предметным областям. Например, экран операций получает кошельки из `data-access/wallets`, а справочники — из `data-access/reference-data`.
- `core` — авторизация и общая инфраструктура приложения.
- `shared` — переиспользуемые элементы без зависимостей от конкретных экранов.
- Компонент, шаблон, стили и тест лежат рядом.
- Модели состояния экрана остаются в его feature; в `data-access` выносятся только модели API.
- Feature не импортирует другую feature. Общие зависимости доступны через `data-access`, `core` и `shared`; эти каталоги не зависят от features. Граф зависимостей должен оставаться без циклов.

### 4. Короткие проверяемые конвенции

При реализации создать `docs/conventions/repository-structure.md`, `backend.md` и `frontend.md`. Они отвечают на вопросы: куда положить файл, как назвать, от чего он может зависеть, где его тест и когда код становится общим.

- Не создавать новые неопределённые папки `Helpers`, `Utils`, `Common`, `Misc`. Использовать предметные имена: `Money`, `Pagination`, `Authentication`.
- C# — PascalCase для папок и файлов типов; frontend — kebab-case, с явным назначением (`*-api.service.ts`, `*-page.component.ts`).
- Doc-комментарии в коде (XML `<summary>`/`<param>` в C#, JSDoc в TypeScript) — только на английском, независимо от языка остальной документации проекта.
- Doc-комментарии — сжатые: что делает метод/класс и краткое назначение параметров, без истории изменений, без пересказа реализации и без комментариев к очевидному коду. Комментарий пишется только там, где неочевидна причина (ограничение, инвариант, обход бага); при отсутствии такой причины — не писать.
- Общий код выделять по реальному использованию и назначению; локальный код оставлять у владельца.
- Backend-тесты сохранять в двух существующих тестовых проектах, с группировкой по модулям и при необходимости сценариям; frontend-тесты хранить рядом с проверяемыми файлами.
- Историю изменений вести в `docs/PROGRESS.md`, причины архитектурных решений — в ADR. Комментарии в коде должны объяснять актуальные ограничения и неочевидные решения; содержательные ссылки на ADR сохранять. Массовую редактуру комментариев не смешивать с первым переносом.
- Закрепить правила зависимостей автоматическими проверками: запрет импортов между frontend-features и запрет зависимостей Domain от Infrastructure. Backend-проверки должны учитывать принятые ADR, а не вводить новые ограничения задним числом.

## Границы первого этапа

Допустимы переносы, согласованные переименования файлов/типов, обновления импортов, namespace при необходимости, путей solution/ProjectReference, сборки и документации. Имена сборок сохраняются. Миграции переносятся вместе со snapshot и designer-файлами без изменения идентификаторов и SQL.

Не входят: объединение .NET-проектов, изменение бизнес-логики, HTTP-контрактов, схемы БД, транзакций, авторизации, планировщиков, UI-поведения, замена библиотек или настройка облачных аккаунтов. Новые бизнес-требования не вводятся.

## Последствия и альтернативы

- Одинаковое размещение файлов уменьшает время поиска; отдельные корни backend/frontend соответствуют независимым сборкам и деплоям.
- Доступ к данным перестаёт принадлежать экрану, который первым его использовал. Компромисс: переход от экрана к HTTP-клиенту требует открыть другой каталог.
- Перенос затрагивает много путей, импортов и ссылок документации. Выполнять его небольшими проверяемыми шагами, начиная с Wallets как образца.
- 30 backend-проектов сохраняются. Объединение четырёх проектов модуля в один уменьшило бы solution, но убрало бы часть компиляционных ограничений слоёв; это отдельное решение после оценки результата структурного этапа.
- Полная перепись под другую архитектуру и добавление новых абстракций не решают задачу первого этапа и увеличивают риск изменения поведения.

## План и критерии завершения

Исполняемый план и статусы находятся только в [docs/PROGRESS.md](../../PROGRESS.md#план-структурный-рефакторинг-2026-09-12). Этот ADR фиксирует предложенную структуру и её обоснование.

Этап завершён, когда размещение соответствует конвенциям, сборки и существующие тесты проходят, ссылки и команды запуска актуальны, API/схема БД/поведение сохранены. Перенос миграций проверяется обнаружением всех существующих миграций и запуском на одноразовой БД; production-БД для проверки не используется.
