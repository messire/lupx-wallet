## РЕЖИМ ОРКЕСТРАЦИИ

Применяется при работе через `/pipeline` и при выполнении фазы/roadmap целиком, а не одной небольшой правки.

**Выполнять весь заданный объём за один заход**, не возвращать управление пользователю после каждого пункта. Использовать конвейер суб-агентов из `~/.claude/agents/` (`feature-planner` → реализующие агенты → `tdd-test-engineer` → `code-quality-reviewer`/`ux-parity-reviewer` → `architecture-documenter`) и паттерн `CLARIFICATION_NEEDED` — суб-агент не спрашивает пользователя напрямую, формулирует вопрос основному агенту с вариантами A/B/C.

### Делегирование и параллелизм (обязательно)

Основной агент — координатор, не исполнитель: не пишет код/тесты/ревью сам, если для этого есть профильный суб-агент. Независимые пункты (не пересекаются по файлам/модулям/схеме БД) запускать **одним сообщением с несколькими вызовами Task/Agent**, не последовательно — последовательный запуск независимых пунктов является анти-паттерном. Для этого проекта независимость определяется границами модулей (`high-level-architecture.md`, §2): например, `ExchangeRates`, `Reporting`, `Audit` не пересекаются друг с другом ни по коду, ни по схеме БД — их backend можно и нужно строить параллельно тремя разными вызовами `backend-services-engineer`. Angular UI для уже готового backend-среза можно вести параллельно с backend'ом следующего среза, если они не делят одни и те же файлы фронтенда. Ревьюеры (`code-quality-reviewer` + `ux-parity-reviewer`) — всегда параллельно, это уже было зафиксировано.

### Артефакты (обязательно)

Каждый вызов суб-агента должен явно указывать целевой файл-артефакт для результата — агент не должен возвращать содержательный результат только текстом в чат:
- План/декомпозиция → `docs/PROGRESS.md` (этот проект не использует `docs/PLANS/`).
- Архитектурное решение → новый ADR в `docs/architecture/adr/`.
- Тесты → `backend/tests/LupexWallet.UnitTests/` или `backend/tests/LupexWallet.IntegrationTests/`, по существующей структуре.
- Находки ревью (`code-quality-reviewer`/`ux-parity-reviewer`) — если тривиальны и сразу исправлены, фиксируются одной записью в `docs/PROGRESS.md` (раздел «Баги, найденные и исправленные», по образцу уже сделанного); если требуют отдельного решения пользователя — оформляются как самостоятельный пункт для следующего цикла, не теряются в истории чата.
- Код/UI — сами файлы реализации, как обычно.

Это нужно, чтобы результат этапа был пригоден для другого агента/скилла без доступа к текущей истории диалога — только к файлам репозитория.

### Сжатие контекста (обязательно)

Суб-агенты уже изолированы по контексту (отдельный вызов Task/Agent) — не читать их полные транскрипты в основной сессии без необходимости, полагаться на итоговую сводку (формат CRITICAL/RECOMMENDED) и файл-артефакт. Основной агент после каждого цикла (план → реализация → тесты → ревью) фиксирует в `docs/PROGRESS.md` только итог — не пересказывает промежуточные детали цикла в последующих сообщениях пользователю или в промптах следующим агентам; следующий шаг конвейера отталкивается от текущего состояния `docs/PROGRESS.md`/`pipeline-state.json`, а не от полной истории диалога. При многоитерационных циклах (architect↔reviewer, макс. 2-3 итерации) держать в явном виде только последнюю итерацию и её результат, не всю цепочку.

### Критичный стоп (спросить пользователя, остановить конвейер)

Только:
1. **Неоднозначность бизнес-требований**, не закрываемая существующими `docs/requirements/*`, ADR или `docs/PROGRESS.md`. В частности — пункты, уже явно помеченные в `docs/PROGRESS.md` («Известные упрощения / TODO») как «требует явного запроса/обсуждения перед реализацией», должны быть закрыты с пользователем **до** старта автономного прогона той части конвейера, которую они блокируют.
2. **Необратимые/деструктивные действия**: изменения схемы БД, теряющие данные, `git push --force`, удаление веток/тегов, продакшн-деплой — см. `git-surgeon`, вне обычного конвейера.
3. **Конфликт между уже принятыми ADR** (не между ADR и новой хотелкой — это пункт 1).

### Не критично (решать самостоятельно, не спрашивать)

Технические детали реализации в рамках уже зафиксированной архитектуры (`ddd-model.md`, `high-level-architecture.md`, принятые ADR): выбор конкретного подхода к реализации, структура тестов, порядок работы по пунктам плана, оформление ADR по факту принятого решения. «Ask about ambiguity» выше относится к **бизнес**-требованиям, а не к инженерным решениям внутри уже согласованной архитектуры.
