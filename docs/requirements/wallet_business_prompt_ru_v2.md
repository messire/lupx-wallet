# Промпт: приложение для личного учета финансов

Нужно разработать однопользовательское приложение для личного учета финансов.

Приложение создается только для одного пользователя. Не нужны регистрация, роли, права доступа, совместные кошельки и многопользовательские сценарии.

## Цель

Пользователь должен видеть свои деньги в разных кошельках и валютах, учитывать доходы, расходы, переводы и корректировки, а также смотреть текущий и исторический баланс.

## 1. Кошельки

Пользователь может создавать несколько кошельков.

Каждый кошелек имеет:

- название;
- валюту;
- тип;
- назначение или понятное пользователю описание;
- начальный баланс;
- дату начала учета;
- признак включения в общую сумму;
- признак основного кошелька;
- возможность архивирования;
- ручной порядок отображения;
- необязательные цвет и иконку.

Кошельки могут отличаться валютой и назначением.

Удалять кошелек с историей операций не нужно. Вместо удаления используется архивирование.

Одновременно может быть выбран один основной кошелек.

Валюта основного кошелька является основной валютой отображения приложения. Отдельной настройки «валюта приложения» нет.

Если основной кошелек меняется, общая сумма начинает отображаться в валюте нового основного кошелька.

В текущую общую сумму входят только кошельки, для которых включен соответствующий признак.

На первом этапе не нужно реализовывать:

- разделение фактического и доступного баланса;
- кредитные лимиты и задолженность.

При этом развитие приложения в эту сторону в будущем не должно быть искусственно заблокировано.

## 2. Курсы валют

Курсы валют загружаются из общедоступного бесплатного сервиса.

Обновление выполняется:

- автоматически раз в три часа;
- вручную по кнопке.

После ручного обновления трехчасовой таймер запускается заново.

Если новый курс получить не удалось, используется последний успешно загруженный курс.

Приложение должно показывать дату и время последнего успешного обновления курсов.

Точность курса используется в том виде, в котором ее предоставляет внешний сервис.

Курсы нужны для пересчета общей суммы в валюту основного кошелька и для отображения исторических данных.

## 3. Операции

На первом этапе поддерживаются четыре базовых вида операций:

- доход;
- расход;
- перевод;
- ручная корректировка баланса.

Операция должна ссылаться на тип по его идентификатору.

Типы операций не должны быть жестко зашиты в приложение как закрытый enum. Пользователь должен иметь возможность добавлять новые типы операций без обновления приложения, если новый тип укладывается в уже поддерживаемое поведение.

Например, пользователь может добавить отдельные типы:

- зарплата;
- возврат долга;
- продукты;
- коммунальные расходы;
- комиссия;
- кэшбэк.

Добавление нового принципиально иного поведения операции может требовать обновления приложения.

Операции можно редактировать.

Любые изменения операций должны полностью фиксироваться в аудите.

## 4. Переводы

Перевод между кошельками разрешен только в том случае, если оба кошелька имеют одинаковую валюту.

Один перевод представлен двумя связанными операциями:

- списание из исходного кошелька;
- зачисление в целевой кошелек.

Обе операции являются частями одного перевода и должны обрабатываться как единое действие с точки зрения пользователя.

## 5. Баланс

У каждого кошелька есть текущий баланс.

Также ведется история баланса в виде ежедневных слепков.

Слепок баланса создается или обновляется ежедневно в 12:00 UTC.

Для одного кошелька должна существовать одна запись истории баланса на одну дату.

Если в эту дату была выполнена ручная корректировка или изменились данные, влияющие на баланс за эту дату, соответствующий слепок должен быть обновлен.

Пользователь должен иметь возможность посмотреть баланс кошелька на выбранную дату.

Историческая общая сумма отображается в валюте текущего основного кошелька с использованием курса, актуального для соответствующей даты. Если точного курса нет, используется последний известный курс на тот момент.

## 6. Аудит

Приложение должно вести подробный аудит любых изменений финансовых данных.

Аудит должен охватывать как минимум:

- создание;
- редактирование;
- удаление или отмену;
- ручные корректировки;
- создание слепка баланса;
- обновление слепка баланса;
- связанные изменения при переводах.

По аудиту должно быть возможно понять:

- что изменилось;
- когда изменилось;
- какая запись была затронута;
- какое значение было до изменения;
- какое значение стало после изменения;
- изменение было выполнено пользователем или системой.

История аудита не должна теряться при последующих изменениях данных.

## 7. Расширяемые справочники

Все наборы значений, которые могут разумно расширяться без обновления приложения, должны храниться как отдельные редактируемые справочники, а бизнес-сущности должны ссылаться на них по идентификатору.

Это относится, например, к:

- типам кошельков;
- типам операций;
- другим расширяемым классификаторам, которые появятся позже.

Не нужно превращать в справочники значения с жестко ограниченной природой, например обычные логические признаки «да/нет».

Главный принцип: если пользователь потенциально может добавить новый вариант без появления новой бизнес-логики, такой набор не должен быть закрытым enum в коде.

## 8. Ограничения первого этапа

На первом этапе не нужны:

- категории и сложная аналитика расходов;
- бюджеты;
- регулярные платежи;
- долги;
- кредитные продукты;
- импорт банковских выписок;
- совместный доступ;
- роли и права;
- синхронизация между несколькими пользователями.

Сначала нужно реализовать надежную базу:

- кошельки;
- курсы валют;
- операции;
- переводы;
- текущий баланс;
- историю баланса;
- аудит;
- расширяемые справочники.

## 9. Технологический стек

Использовать следующий стек:

- frontend: Angular;
- backend: ASP.NET Core;
- ORM: Entity Framework Core;
- база данных: PostgreSQL;
- фоновые задачи: стандартные средства ASP.NET Core;
- общий подход: модульный монолит.

Не заменять согласованные технологии без прямого указания пользователя.

## 10. Язык и правила работы

Все, что связано с программным кодом, должно быть на английском языке.

На английском языке должны быть, в частности:

- имена проектов и модулей;
- имена файлов и папок;
- классы, интерфейсы, методы, свойства и переменные;
- названия таблиц, колонок и других объектов базы данных;
- маршруты API;
- системные коды и идентификаторы;
- комментарии в коде;
- сообщения логов;
- технические сообщения об ошибках.

Документация, бизнес-описания, пояснения и общение с пользователем должны быть на русском языке.

Ничего не додумывать и не принимать скрытых решений за пользователя.

Если требование допускает несколько трактовок, содержит противоречие или неясно, как именно должна работать функция, необходимо остановиться и задать пользователю конкретный уточняющий вопрос.

Не выбирать архитектуру, структуру данных, поведение интерфейса или бизнес-правило на основании личных предположений.

Уточняющий вопрос должен описывать конкретную двусмысленность и возможные варианты, а не быть общим вопросом в духе «что вы хотите сделать».

## 11. Требование к результату

Не придумывай дополнительные бизнес-функции без необходимости.

Не переходи к проектированию архитектуры, структуры базы данных, классов, API или интерфейсов, пока это не будет запрошено отдельно.

Сначала используй это описание как источник бизнес-требований.

Если обнаружена двусмысленность, противоречие или отсутствует решение, без которого нельзя продолжать, сначала задай пользователю конкретный уточняющий вопрос. Не подменяй отсутствующее решение собственным предположением.
