# ADR-0007: Синхронные gateway-контракты между модулями вместо событий там, где эффект обязателен для успеха команды

## Статус

Принято

## Контекст

`ddd-model.md` (§6, таблица команд Operations) описывала эффект «`CreateOperation` → `OperationCreated` → Wallets: обновление `CurrentBalance`» как побочный эффект доменного события. При реализации среза Operations выяснилось, что для этого сценария нужна не только доставка события, но и:

1. **Разрешение поведения типа операции** — `Operation` ссылается на `OperationTypeId` (модуль ReferenceData), но сам не знает, увеличивает или уменьшает сумма баланс — это определяется через `OperationType.BehaviorKindId`. Без этого невозможно вычислить знак эффекта на баланс уже в момент создания команды.
2. **Обязательность эффекта для успеха самой команды** — если кошелёк не существует или его валюта не совпадает с валютой операции, создание операции должно быть отклонено целиком, а не «создать операцию, а потом попытаться обновить баланс и откатить по ошибке из обработчика события». Технически откат транзакции в обоих случаях работает одинаково (общий `TransactionScope`), но чисто событийная схема (публикация в `SavingChangesAsync`, обработка в отдельном `INotificationHandler`) добавляет косвенность там, где эффект на самом деле является частью основной бизнес-логики команды, а не независимой реакцией другого модуля.

Событийная схема также потребовала бы, чтобы `Wallets.Application` ссылался на `Operations.Domain` ради типов событий — новая связь Domain-к-Domain между модулями, не предусмотренная явно в `high-level-architecture.md` §2 (там названы только «ссылка по Id», «доменное событие» и «узкий read-only контракт», без уточнения, что публикация событий может потребовать прямой ссылки на чужой Domain-проект).

## Решение

Для сценариев, где эффект в другом модуле **обязателен для корректности самой команды** (а не является независимой реакцией), используется **явно опубликованный узкий синхронный контракт** (уже допустимый способ связи из `high-level-architecture.md` §2, пункт 3), а не доменное событие:

1. **`ReferenceData.Application.IOperationTypeLookup`** — читает `OperationType` (активность, `BehaviorKindId`/код) и умеет найти активный тип с заданным поведением (используется при создании перевода — см. ниже). Реализация в `ReferenceData.Infrastructure`.
2. **`Wallets.Application.IWalletBalanceGateway`** — читает валюту/архивность/текущий баланс кошелька и применяет знаковую дельту к `CurrentBalance`. Реализация в `Wallets.Infrastructure`, работает через тот же `WalletsDbContext`/`SaveChangesAsync`, поэтому участвует в общем `TransactionScope` команды без дополнительной оркестрации.

`Operations.Application` ссылается на `ReferenceData.Application` и `Wallets.Application` (только эти публичные интерфейсы, не на `*.Domain`/`*.Infrastructure` других модулей) — согласуется с правилом границы модуля.

Доменные события (`OperationCreated`, `OperationUpdated`, `OperationDeleted`, `TransferCreated`, `TransferDeleted`) по-прежнему поднимаются агрегатами `Operation`/`Transfer` и публикуются через `DispatchDomainEventsInterceptor` — они остаются точкой расширения для будущих **необязательных** реакций (Audit, BalanceHistory), которые не обязаны выполниться синхронно для успеха самой команды создания операции.

## Последствия

- Уточняет правило границы модуля из `high-level-architecture.md` §2: список из трёх разрешённых связей («по Id», «событие», «узкий контракт») остаётся в силе, но добавляется критерий выбора между «событие» и «синхронный контракт» — обязательный для успеха команды эффект в чужом модуле выражается синхронным контрактом, необязательная реакция — событием.
- `Operations.Application` получает два новых ProjectReference (`ReferenceData.Application`, `Wallets.Application`) — граф зависимостей модулей перестаёт быть «только Host знает про все модули», появляется прямая зависимость одного модуля от Application-слоя двух других. Это осознанный компромисс модульного монолита (не микросервисов): все модули всё равно живут в одном процессе и одной базе, синхронный вызов интерфейса ничем не дороже события с точки зрения производительности, а корректность (отказ команды целиком при недоступности кошелька) выражается проще.
- Домен `Operation`/`Transfer` не зависит от `ReferenceData`/`Wallets` напрямую — только `Operations.Application` (уровень оркестрации use case), что сохраняет чистоту доменного слоя.
- Если в будущем модуль Operations потребуется вынести в отдельный сервис (маловероятно для однопользовательского приложения, но теоретически), эти два интерфейса — точное место, которое придётся заменить на сетевые вызовы/сагу.

## Альтернативы

- **Событийная схема как в исходном `ddd-model.md`** (Wallets подписывается на `OperationCreated` через `INotificationHandler`) — отклонено: требует ссылки `Wallets.Application → Operations.Domain` ради типов событий и усложняет обработку ошибок валидации (несуществующий кошелёк, несовпадение валюты) без выигрыша в корректности, так как транзакционная граница всё равно общая.
- **Полный отказ от разделения модулей для этого сценария** (например, слияние Wallets и Operations в один модуль) — отклонено: противоречит границам bounded context из `ddd-model.md` и ADR-0006.
