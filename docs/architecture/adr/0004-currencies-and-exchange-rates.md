# ADR-0004: Валюты и курсы — Frankfurter, доступные и активные валюты, обновление, история курсов

## Статус

Принято. Пересобрано 2026-09-30 из решений от августа 2026 (Q5, Q6), 2026-09-11 (механизм обновления), 2026-09-16 и 2026-09-30 (списки валют, API v2, исторические курсы).

**Состояние реализации:** частично. Что именно в коде работает по прежним правилам — в разделе «Состояние реализации».

## Контекст

Раздел 2 требований: курсы загружаются из общедоступного бесплатного сервиса, обновляются автоматически, могут быть обновлены вручную с перезапуском таймера, при ошибке используется последний успешный курс, точность — как отдаёт сервис. Общая и историческая общая сумма выражаются в валюте текущего основного кошелька, который пользователь может сменить в любой момент.

Проверка 2026-09-30 показала, что приложение привязано к Frankfurter API v1 (адрес по умолчанию `api.frankfurter.app` перенаправляет на `api.frankfurter.dev/v1`), а список валют для выбора берётся из статического файла на 159 валют, не связанного с сервисом. Факты о сервисе, установленные запросами:

- v1 отдаёт 30 валют; RUB, KZT, BYN, UAH в нём нет.
- v2 (`api.frankfurter.dev/v2`): `GET /v2/currencies` вернул 166 валют, курс RUB→EUR получен. Сайт заявляет 208 валют; причина разницы не проверялась.
- Криптовалют нет ни в одной версии.
- Формат v2 другой: `rates?base=X&quotes=Y`, ответ — массив `[{date, base, quote, rate}]`; поддерживаются период (`from`/`to`) и несколько валют назначения в одном запросе. Ограничение на длину периода не проверялось.

## Решение

### 1. Источник

Frankfurter, **API v2**, без ключа и регистрации. Клиент — `FrankfurterClient` через `IHttpClientFactory`, до трёх попыток с нарастающей задержкой при сетевой ошибке, таймауте или 5xx. Точность курса — как отдаёт сервис, без округления.

### 2. Периодичность

Автообновление раз в сутки. Это осознанное изменение исходного требования «раз в три часа» (Q5), зафиксированное в [user-scenarios.md](../../requirements/user-scenarios.md), раздел «Изменения исходных требований».

### 3. Ручное обновление

По кнопке, вне очереди, синхронно в HTTP-запросе. После ручного обновления — успешного или нет — суточный отсчёт начинается заново от этого момента: эндпоинт сообщает об этом фоновому сервису сигналом `NotifyManualRefreshCompleted` (без повторного обновления).

### 4. Пары курсов

Курсы запрашиваются напрямую как пара «активная валюта → валюта текущего основного кошелька». Промежуточная базовая валюта и кросс-курсы не используются. Пара валюты с самой собой пропускается. Без основного кошелька обновление не выполняется. Обновляются только **активные** валюты (§7).

### 5. Смена основного кошелька

При смене основного кошелька курсы всех активных валют перезапрашиваются к новой основной валюте. Подписчик `PrimaryWalletChangedHandler` не делает HTTP-вызов: он сигналит фоновому сервису (`RequestRefresh`), а обновление выполняется вне транзакции команды `SetPrimaryWallet` ([ADR-0001](./0001-modular-monolith.md), §7). Между сменой и обновлением есть короткое окно, в котором отдаются курсы к прежней основной валюте; курсы к прежней валюте удаляются при следующем обновлении.

Плановый прогон, старт приложения, ручное обновление и реакция на смену основного кошелька — одна команда `RefreshExchangeRatesCommand`. Она намеренно не `ICommand`: HTTP-вызовы не должны идти внутри `TransactionScope` (ADR-0001, §4); атомарность — один `SaveChanges` на прогон.

### 6. Отказоустойчивость

- При ошибке запроса по паре сохраняется последний успешно загруженный курс, дата его получения не меняется. Ручное обновление при недоступности источника отвечает 502, но не стирает уже показанные курсы.
- Валюта, которую сервис не поддерживает, пропускается молча — это постоянное свойство валюты, а не сбой.
- Если сервис убрал валюту, она исчезает из доступных (§7); если она при этом активна — остаётся активной с последним известным курсом.

### 7. Доступные и активные валюты

- **Доступные валюты** — те, что отдаёт сервис. Хранятся в БД и обновляются вместе с курсами. Пользователь ими не управляет. Нужны только для списков выбора: при создании кошелька и при добавлении валюты в активные.
- **Активные валюты** — те, которые использует пользователь; ими он управляет сам: добавляет из доступных и убирает, если валюта не используется ([ADR-0002](./0002-record-lifecycle.md), §4).
- При создании кошелька валюта выбирается из доступных и **автоматически становится активной**.
- Состояния «деактивирована» у валюты нет.
- Названия валют — английские, из сервиса. Произвольный код не принимается; криптовалюты не поддерживаются.

### 8. Чтение только из БД

Приложение читает курсы и валюты только из БД. Обращений к сервису в момент чтения данных (в том числе при расчёте общей суммы за прошлую дату) нет.

### 9. Исторические курсы

Когда валюта становится активной, фоновый сервис дозагружает её курсы за период от самой ранней даты начала учёта до сегодняшнего дня (один запрос на валюту, §«Контекст»). При смене основного кошелька дозагрузка повторяется по всем активным валютам к новой основной валюте. Пока дозагрузка не завершена, общая сумма за прошлые даты неполная: кошельки без курса исключаются из суммы с указанием причины. Для даты без курса (выходной) используется ближайший более ранний.

## Последствия

- Добавление валюты в активные и создание кошелька запускают сетевую работу в фоне; смена основного кошелька — перезагрузку всей истории курсов.
- Обновление — по одному запросу на активную валюту, последовательно; при недоступности источника несколько пар × три попытки могут занимать минуты, что и исключает `TransactionScope` (§5).
- По валюте, оставшейся только в архивных кошельках, курс продолжает обновляться.
- Приложение зависит от одного внешнего сервиса; при его длительной недоступности курсы «замораживаются» — это предписано требованиями.
- Обоснование [ADR-0005](./0005-money-precision.md) криптовалютами теряет силу; само решение о точности не меняется.
- Фоновый сервис `ExchangeRateRefreshBackgroundService` несёт три обязанности: обновление курсов, обновление списка доступных валют, дозагрузку истории. Сигнал в памяти теряется при перезапуске — следующий плановый прогон покрывает это.
- Список доступных валют загружает `ExchangeRates`, а справочник `Currency` принадлежит `ReferenceData`; где хранится список и каким портом модули связаны — инженерное решение этапа реализации в рамках ADR-0001, §2.

## Состояние реализации

Код на 2026-09-30:

- Клиент использует API v1 (`latest?base=&symbols=`, `{date}?base=&symbols=`); нужен новый формат запросов и ответов.
- Список валют для выбора — статический `frontend/src/app/shared/currencies/iso-currencies.ts`; backend принимает любой код. Файл удаляется.
- Курсы обновляются по всем валютам справочника, включая деактивированные (решение от 2026-09-16, отменено §7).
- У валюты есть состояние «деактивирована» (ADR-0002, «Состояние реализации»).
- `ExchangeRateLookup.GetOrFetchHistoricalRateAsync` обращается к сервису и пишет кэш в БД во время `GET /reporting/total-amount` — противоречит §8; заменяется дозагрузкой §9.
- Реализованы и соответствуют ADR: периодичность, ручное обновление с сигналом, реакция на смену основного кошелька через канал, отказоустойчивость, удаление устаревших пар, единая команда обновления.

Меняются `docs/api/openapi.yaml`, схемы `reference_data` и `exchange_rates`, экраны справочника валют, создания кошелька и курсов.

## Отклонённые варианты

- **Фиксированная базовая валюта с кросс-курсами на стороне приложения** — пользователь предпочёл прямые пары без промежуточной валюты (Q6).
- **Другой источник курсов** — не рассматривался, сервис назван пользователем.
- **Синхронный HTTP-вызов в подписчике `PrimaryWalletChanged`** — смена основного кошелька зависела бы от внешнего сервиса.
- **Outbox для сигнала обновления** — избыточно; сигнал в памяти достаточен, потеря покрывается плановым прогоном.
- **Один список: все валюты сервиса сразу в справочнике** — пользователь управляет только теми, которыми пользуется.
- **Сохранить деактивацию валюты** — список выбора строится из доступных, третье состояние не нужно.
- **Русские названия из статического файла** — названия всегда из сервиса.
- **Только накопление истории курсов с момента активации** — теряются курсы за прошлые даты.
- **Запрос исторического курса в момент чтения** — нарушает §8.
- **Ручной курс или второй источник для криптовалют** — криптовалюты вне объёма.
