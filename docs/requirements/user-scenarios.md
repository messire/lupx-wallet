# Пользовательские сценарии

Источник требований: [wallet_business_prompt_ru_v2.md](./wallet_business_prompt_ru_v2.md).

Документ описывает сценарии использования приложения личного учета финансов на первом этапе (единственный пользователь, без ролей и совместного доступа).

Обозначения:

- **Actor** — кто инициирует сценарий: `User` (пользователь) или `System` (фоновый процесс приложения).
- Пометка **⚠ Открытый вопрос Qn** означает, что точное поведение в требованиях не определено или противоречиво. Соответствующий вопрос см. в разделе «Открытые вопросы» и в чате с пользователем. До получения ответа сценарий не должен реализовываться на основании предположений.

## 1. Управление кошельками (Wallets)

### UC-01. Создание кошелька
- **Actor**: User
- **Предусловие**: нет.
- **Основной поток**: пользователь указывает название, валюту, тип кошелька (из справочника типов), назначение/описание, начальный баланс, дату начала учета, признак включения в общую сумму, признак основного кошелька (опционально), порядок отображения, опционально цвет и иконку.
- **Результат**: создан новый кошелек с текущим балансом, равным начальному балансу; действие зафиксировано в аудите.
- **Примечания**: наличие основного кошелька в системе обязательно (решено, Q7) — если это первый создаваемый кошелек, он автоматически становится основным.

### UC-02. Редактирование кошелька
- **Actor**: User
- **Основной поток**: пользователь изменяет название, тип, назначение, признак включения в общую сумму, порядок отображения, цвет/иконку и другие атрибуты существующего кошелька. Валюту можно изменить только у кошелька без истории операций и слепков баланса.
- **Результат**: изменения сохранены, зафиксированы в аудите (значение до/после).
- **Решено (Q15)**: смена валюты кошелька запрещена, если по нему уже есть история (операции или слепки баланса) в прежней валюте. Для кошелька без истории смена валюты допускается.

### UC-03. Архивирование кошелька
- **Actor**: User
- **Основной поток**: пользователь архивирует кошелек вместо удаления.
- **Результат**: кошелек помечен как архивный, остается доступным для просмотра истории, но не участвует в дальнейших операциях; действие зафиксировано в аудите.
- **Решено (Q7)**: архивировать текущий основной кошелек запрещено — сначала пользователь должен назначить другой кошелек основным.
- **Решено (Q16)**: архивирование не изменяет автоматически признак «включен в общую сумму» — это независимые атрибуты. Если архивный кошелек не должен учитываться в общей сумме, пользователь обязан выключить флаг вручную.

### UC-04. Удаление кошелька (без истории операций)
- **Actor**: User
- **Основной поток**: пользователь удаляет кошелек, по которому не было операций.
- **Результат**: кошелек окончательно удален (физически, не архивирован).
- **Решено (Q2)**: кошелек без связанной истории операций может быть удален окончательно. Кошелек с историей операций — только архивируется (см. UC-03).

### UC-05. Выбор основного кошелька
- **Actor**: User
- **Основной поток**: пользователь назначает один из существующих кошельков основным.
- **Результат**: прежний основной кошелек теряет признак; общая сумма начинает отображаться в валюте нового основного кошелька; действие зафиксировано в аудите.
- **Решено (Q8)**: основной кошелек всегда учитывается в общей сумме. Признак «включен в общую сумму» принудительно включается при назначении кошелька основным (и не может быть выключен, пока кошелек остается основным).

### UC-06. Изменение порядка отображения кошельков
- **Actor**: User
- **Основной поток**: пользователь вручную переупорядочивает список кошельков.
- **Результат**: новый порядок сохранен и используется при отображении списка.

### UC-07. Просмотр списка кошельков и их текущих балансов
- **Actor**: User
- **Основной поток**: пользователь открывает список кошельков (активных и, по отдельному запросу, архивных) и видит текущий баланс каждого в его собственной валюте.
- **Результат**: список отображен с учетом ручного порядка сортировки.

## 2. Курсы валют (Exchange rates)

### UC-08. Автоматическое обновление курсов
- **Actor**: System
- **Основной поток**: раз в сутки система запрашивает курсы валют из внешнего сервиса Frankfurter.
- **Результат при успехе**: новые курсы сохранены, зафиксированы дата и время обновления.
- **Результат при ошибке**: сохраняется последний успешно загруженный курс; таймер продолжает исходный суточный цикл.
- **Решено (Q5)**: источник курсов — сервис [Frankfurter](https://www.frankfurter.app/) (бесплатный, общедоступный, без ключа). ⚠ Изменение исходного требования: пользователь явно поменял периодичность автообновления с «раз в 3 часа» (раздел 2 исходного документа) на «раз в сутки» — это осознанное изменение бизнес-требования, а не молчаливое допущение (см. раздел «Изменения исходных требований» в конце файла).
- **Решено (Q6)**: курсы запрашиваются напрямую как пара «валюта кошелька → текущая основная валюта» (Frankfurter поддерживает произвольную базовую валюту в запросе). При смене основного кошелька (и, соответственно, основной валюты) курсы перезапрашиваются заново с новой базой; промежуточная фиксированная базовая валюта не используется.

### UC-09. Ручное обновление курсов
- **Actor**: User
- **Основной поток**: пользователь нажимает кнопку обновления курсов.
- **Результат при успехе**: курсы обновлены, суточный таймер автообновления запускается заново от момента ручного обновления.
- **Результат при ошибке**: используется последний успешно загруженный курс; таймер также перезапускается.

### UC-10. Просмотр времени последнего обновления курсов
- **Actor**: User
- **Основной поток**: пользователь видит дату и время последнего *успешного* обновления курсов.
- **Результат**: отображена метка времени последнего успешного обновления.

## 3. Операции (Operations)

### UC-11. Регистрация операции дохода
- **Actor**: User
- **Основной поток**: пользователь создает операцию с типом, ссылающимся на справочник типов операций, относящуюся к базовому поведению «доход»; указывает кошелек, сумму, дату.
- **Результат**: баланс кошелька увеличен; операция зафиксирована в аудите.
- **Примечания**: тип операции может по смыслу совпадать с категорией (см. UC-15, решение по Q1), но не используется для аналитики на этом этапе.

### UC-12. Регистрация операции расхода
- **Actor**: User
- **Основной поток**: аналогично UC-11, но базовое поведение «расход» — баланс кошелька уменьшается.

### UC-13. Редактирование операции
- **Actor**: User
- **Основной поток**: пользователь изменяет сумму, дату, тип, кошелек или иные атрибуты ранее созданной операции, в том числе датированной прошедшим числом.
- **Результат**: изменение сохранено; в аудите зафиксированы значения до и после; система пересчитывает слепки баланса за дату операции и за все последующие даты (см. UC-23).
- **Решено (Q4)**: пересчет каскадный — распространяется на все слепки после даты измененной операции, чтобы накопительная история оставалась корректной.

### UC-14. Удаление операции
- **Actor**: User
- **Основной поток**: пользователь удаляет ранее созданную операцию, не связанную с переводом (см. UC-16) и не входящую в уже сформированный слепок как единственное историческое основание.
- **Результат**: операция окончательно удалена; в аудите зафиксирован факт удаления со значением записи до удаления; система пересчитывает слепки баланса за дату операции и за все последующие даты.
- **Решено (Q2)**: удаление операций без истории/связей допускается окончательно (в отличие от кошельков с историей — те архивируются, не удаляются). Итоговая формулировка ограничения «без истории/связей» для операций (например, операции — части перевода) не уточнялась отдельно и требует подтверждения при проектировании.

### UC-15. Добавление нового типа операции пользователем
- **Actor**: User
- **Основной поток**: пользователь добавляет новый элемент в справочник типов операций (например, «зарплата», «продукты»), если новый тип укладывается в уже поддерживаемое поведение (доход/расход/перевод/корректировка).
- **Результат**: новый тип операции доступен для выбора при создании операций.
- **Решено (Q1)**: типы операций могут выполнять роль категорий (пользователь свободно добавляет «зарплата», «продукты», «кэшбэк» и т.п.), но на первом этапе по ним **не строится аналитика и отчетность** (никаких сумм/графиков в разрезе категории-типа) — это остается ограничением раздела 8.

## 4. Переводы (Transfers)

### UC-16. Перевод между кошельками одной валюты
- **Actor**: User
- **Предусловие**: исходный и целевой кошельки имеют одинаковую валюту.
- **Основной поток**: пользователь указывает исходный кошелек, целевой кошелек и сумму; создаются две связанные операции — списание и зачисление.
- **Результат**: обе операции применяются как единое действие; балансы обоих кошельков обновлены; в аудите зафиксировано перевод целиком, включая связь между двумя операциями.
- **Решено (Q10)**: сумма списания всегда равна сумме зачисления — комиссия за перевод между своими кошельками не поддерживается. Тип операции «комиссия» (пример из раздела 3) — это отдельный, не связанный с переводом расход (например, комиссия банка за обслуживание счета), создаваемый как обычная операция расхода (UC-12).

### UC-17. Попытка перевода между кошельками разных валют
- **Actor**: User
- **Основной поток**: пользователь пытается создать перевод между кошельками с разными валютами.
- **Результат**: операция запрещена правилами раздела 4 требований.
- **Решено (Q9)**: конвертация валют при переводе на первом этапе не предусмотрена вообще; для перемещения денег между кошельками разных валют пользователь вручную создает две несвязанные операции (расход в одном кошельке, доход в другом).

## 5. Баланс и история (Balance)

### UC-18. Просмотр текущего баланса кошелька
- **Actor**: User
- **Результат**: отображен актуальный баланс кошелька в его валюте.

### UC-19. Просмотр общей суммы по всем кошелькам
- **Actor**: User
- **Основной поток**: система суммирует балансы кошельков с включенным признаком «включен в общую сумму», конвертируя их в валюту текущего основного кошелька по актуальному курсу.
- **Результат**: отображена общая сумма.
- **Примечания**: основной кошелек всегда включен в сумму (решено, Q8); наличие основного кошелька гарантировано (решено, Q7), поэтому сумма никогда не может быть «без основы».

### UC-20. Просмотр баланса кошелька на выбранную дату
- **Actor**: User
- **Основной поток**: пользователь выбирает дату; система показывает баланс кошелька на эту дату на основании слепка истории баланса.
- **Результат**: отображен исторический баланс.
- **Решено (Q13)**: для даты раньше «даты начала учета» кошелька баланс считается равным 0.

### UC-21. Просмотр исторической общей суммы на дату
- **Actor**: User
- **Основной поток**: система суммирует исторические балансы кошельков (по слепкам) на выбранную дату, конвертируя их в валюту *текущего* основного кошелька по курсу, актуальному на эту дату (либо последнему известному курсу до этой даты, если точного курса на дату нет).
- **Результат**: отображена историческая общая сумма.

### UC-22. Автоматическое создание/обновление дневного слепка баланса
- **Actor**: System
- **Основной поток**: ежедневно в 12:00 UTC система создает или обновляет по одной записи слепка баланса на каждый кошелек на текущую дату.
- **Результат**: слепок баланса создан/обновлен; действие зафиксировано в аудите.
- **Решено (Q12)**: если приложение не работало в момент 12:00 UTC, пропущенные слепки досоздаются задним числом (при следующем запуске приложения система обнаруживает пропущенные даты и досоздает слепки за них).

### UC-23. Каскадный пересчет слепков баланса при ретроактивном изменении
- **Actor**: System (инициируется действием пользователя)
- **Основной поток**: пользователь вносит ручную корректировку баланса или изменяет/удаляет операцию, влияющую на баланс за прошедшую дату; система обновляет слепок за эту дату и последовательно пересчитывает все слепки за все последующие даты вплоть до сегодняшней.
- **Результат**: вся накопительная история баланса кошелька после затронутой даты остается корректной; каждое обновление слепка зафиксировано в аудите.
- **Решено (Q4)**: пересчет каскадный (все последующие даты), а не только слепок затронутой даты.

### UC-24. Ручная корректировка баланса
- **Actor**: User
- **Основной поток**: пользователь выбирает способ ввода корректировки — либо задает новое абсолютное значение баланса кошелька на дату, либо задает дельту изменения (+/-); система применяет корректировку соответствующим способом.
- **Результат**: баланс кошелька изменен; операция корректировки, выбранный способ ввода (абсолютное значение/дельта) и её влияние на слепок баланса зафиксированы в аудите.
- **Решено (Q3)**: поддерживаются оба способа ввода корректировки, пользователь выбирает нужный при создании корректировки.

## 6. Аудит (Audit)

### UC-25. Просмотр истории изменений записи
- **Actor**: User
- **Основной поток**: пользователь открывает историю аудита для конкретной записи (кошелек, операция, перевод, слепок баланса).
- **Результат**: отображен список изменений с указанием: что изменилось, когда, какая запись затронута, значение до, значение после, кто внес изменение (пользователь или система).
- **Примечания**: история аудита не должна теряться при последующих изменениях данных (append-only по духу требований).

## 7. Справочники (Reference dictionaries)

### UC-26. Просмотр справочника типов кошельков
- **Actor**: User

### UC-27. Просмотр справочника типов операций
- **Actor**: User

### UC-28. Добавление элемента справочника (тип кошелька / тип операции)
- **Actor**: User
- **Основной поток**: пользователь добавляет новый элемент справочника, если он укладывается в уже поддерживаемое поведение системы.
- **Решено (Q11)**: элемент справочника, уже используемый существующими записями, нельзя удалить — только деактивировать (скрыть из выбора для новых записей), по аналогии с архивированием кошельков.

## 8. Явно вне рамок первого этапа

Согласно разделу 8 исходных требований, следующие сценарии **не реализуются** на первом этапе (перечислены для полноты картины и трассируемости, без описания потока):

- сложная аналитика и отчетность по категориям/типам операций (решено по Q1: сами типы-категории добавлять можно, см. UC-15, но отчетности по ним на этом этапе нет);
- бюджеты;
- регулярные платежи;
- долги;
- кредитные продукты;
- импорт банковских выписок;
- совместный доступ, роли и права;
- синхронизация между несколькими пользователями;
- разделение фактического и доступного баланса, кредитные лимиты и задолженность (при этом архитектура не должна блокировать их добавление в будущем).

## Открытые вопросы, влияющие на сценарии

Все вопросы Q1–Q16, поднятые при анализе исходных требований, решены пользователем; решения отражены в соответствующих сценариях выше пометкой «Решено (Qn)». Пометок ⚠ без решения в этом документе больше не осталось. Итоговый свод решений — см. таблицу ниже.

| № | Вопрос (кратко) | Решение |
|---|---|---|
| Q1 | Тип операции vs категория | Тип операции выполняет роль категории; отчетности/аналитики по типам на первом этапе нет |
| Q2 | Удаление кошельков/операций | Кошельки и операции без истории/связей удаляются окончательно; с историей — только архивирование/сохранение записи |
| Q3 | Способ ручной корректировки | Поддерживаются оба способа: абсолютное значение и дельта — выбирает пользователь |
| Q4 | Каскадный пересчет истории | Пересчитываются все слепки баланса после затронутой даты |
| Q5 | Источник курсов валют | Сервис Frankfurter; периодичность автообновления изменена с 3 часов на 1 сутки (см. «Изменения исходных требований») |
| Q6 | Модель кросс-курсов | Прямой запрос пары «валюта кошелька → текущая основная валюта»; при смене основного кошелька курсы перезапрашиваются с новой базой |
| Q7 | Обязательность основного кошелька | Основной кошелек обязателен всегда; архивировать текущий основной нельзя |
| Q8 | Основной кошелек и общая сумма | Основной кошелек всегда включен в общую сумму, флаг принудительно включен |
| Q9 | Кросс-валютные переводы | Не поддерживаются; пользователь делает две несвязанные операции вручную |
| Q10 | Тип операции «комиссия» | Обычный расход, не связанный с переводом; комиссия за перевод между своими кошельками не предусмотрена |
