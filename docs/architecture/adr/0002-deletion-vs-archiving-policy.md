# ADR-0002: Политика удаления против архивирования/деактивации

## Статус

Принято

## Контекст

Исходные бизнес-требования (раздел 1) прямо предписывают архивирование вместо удаления только для одного случая — «удалять кошелек с историей операций не нужно». Раздел 6 (аудит) при этом упоминает «удаление или отмену» как отдельно отслеживаемое действие, а раздел 7 вводит расширяемые справочники (типы кошельков, типы операций), не уточняя их жизненный цикл. Это порождало неоднозначность (открытые вопросы Q2 и Q11 в [user-scenarios.md](../../requirements/user-scenarios.md)): что именно можно удалять окончательно, а что — только скрывать/деактивировать.

Ответы пользователя дали единый принцип, применимый сразу к нескольким типам сущностей: кошелькам, операциям и элементам справочников.

## Решение

Единое правило для всех перечисленных сущностей: **если у сущности есть связанные данные (история), она не удаляется физически, а только помечается как неактивная; если связанных данных нет — сущность можно удалить окончательно.**

Конкретно:

- **Wallet** — кошелек с историей операций/слепков баланса архивируется (не удаляется); кошелек без истории удаляется окончательно (решено, Q2).
- **Operation** — операция, не связанная с переводом и не единственное историческое основание уже созданного слепка баланса, удаляется окончательно, с фиксацией в аудите значения записи до удаления и последующим каскадным пересчетом слепков баланса (см. ADR-0003). Точная граница «связанности» для операций — часть перевода, участие в уже зафиксированном слепке — требует дополнительного уточнения на этапе проектирования домена (см. «Открытые вопросы» ниже).
- **Reference dictionary item** (тип кошелька, тип операции) — элемент, уже используемый существующими записями, деактивируется (скрывается из выбора для новых записей), но не удаляется; неиспользуемый элемент можно удалить окончательно (решено, Q11, по аналогии с кошельками).

Технически это означает, что в модели данных для этих трех типов сущностей нужен явный признак активности/архивности (например, `IsArchived` / `IsActive`), а не полагаться только на физическое удаление строки.

## Последствия

- Единообразный паттерн упрощает доменную модель: одна и та же логика проверки «есть ли связанные данные» применяется к трем разным сущностям.
- Требуется явно определить для каждой сущности, что считается «связанными данными», блокирующими физическое удаление (для Wallet это очевидно — наличие операций; для Operation и для элементов справочника границу нужно уточнить при проектировании — см. открытый пункт ниже).
- Аудит должен одинаково фиксировать оба вида «исчезновения» записи — физическое удаление и деактивацию/архивирование — с сохранением значения записи до изменения (согласовано с разделом 6 требований).
- Индексы/фильтры на уровне запросов должны по умолчанию скрывать архивные/деактивированные записи из «активных» списков, но обеспечивать их видимость в истории/отчетах.

## Открытый пункт для проектирования домена

Точное определение «связанности», блокирующее удаление операции (участие в переводе, использование как единственное основание уже зафиксированного слепка баланса), не было предметом отдельного уточняющего вопроса и должно быть решено при проектировании доменной модели, а не додумано в этом ADR.

## Альтернативы

- **Полный soft-delete для всех сущностей без исключений** (никогда не удалять физически) — отклонено пользователем: явно подтверждено, что кошельки и операции без истории/связей можно удалять окончательно (Q2).
- **Полное физическое удаление везде, без архивирования** — отклонено требованиями раздела 1 (архивирование прямо предписано для кошельков с историей) и ответом на Q11 для справочников.
