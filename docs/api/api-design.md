# API-контракты

Источники: [openapi.yaml](./openapi.yaml) (машиночитаемая спецификация, провалидирована `@redocly/cli lint` — 0 ошибок), [ddd-model.md](../architecture/ddd-model.md), [high-level-architecture.md](../architecture/high-level-architecture.md), [schema.md](../database/schema.md).

## Ресурсная модель

| Ресурс | Модуль | Соответствует |
|---|---|---|
| `/wallets` | Wallets | агрегат `Wallet` |
| `/wallet-types`, `/operation-types` | ReferenceData | пользовательские справочники |
| `/currencies` | ReferenceData | справочник **активных** валют пользователя (агрегат `Currency`) |
| `/currencies/available` | ReferenceData | список доступных валют сервиса курсов (`AvailableCurrency`, только чтение) |
| `/operation-behavior-kinds` | ReferenceData | системный справочник (только чтение) |
| `/operations` | Operations | агрегат `Operation` |
| `/wallets/{id}/stated-balances/{date}` | Operations | команда `SetStatedBalance` над агрегатом `Operation` (корректирующая запись, ADR-0003 §6); отдельного ресурса заявленного баланса нет |
| `/transfers` | Operations | агрегат `Transfer` |
| `/wallets/{id}/balance`, `/wallets/{id}/balance-history` | BalanceHistory | агрегат `BalanceSnapshot` |
| `/exchange-rates/*` | ExchangeRates | агрегат `ExchangeRateQuote` |
| `/reporting/total-amount` | Reporting | композиция без собственного агрегата |
| `/audit-entries` | Audit | агрегат `AuditEntry` |
| `/auth/login` | Host (сквозная забота) | не доменный ресурс |

Один REST-ресурс = один агрегат (кроме `/reporting/*`, которое намеренно нарушает это правило, так как Reporting — чисто читающая композиция, не агрегат — см. `ddd-model.md`). Переводы не смешаны с операциями в одном ресурсе: `POST /operations` создает только Income/Expense/Adjustment (корректировка — только дельтой; заявленный баланс вводится отдельным `PUT /wallets/{id}/stated-balances/{date}`), для перевода — отдельный `POST /transfers`, отражающий, что перевод — самостоятельный агрегат, координирующий две операции атомарно (раздел 4 требований, `ddd-model.md` §2.5).

## Аутентификация

Решено на этапе высокоуровневой архитектуры: единый пароль без регистрации/ролей (см. `high-level-architecture.md` §8).

1. `POST /api/v1/auth/login { password }` → `{ token, expiresAt }` (JWT).
2. Все остальные эндпоинты требуют `Authorization: Bearer <token>` (схема `BearerAuth` в OpenAPI).
3. `429 Too Many Requests` на `/auth/login` — защита от подбора пароля (лимит попыток на уровне `Host`, деталь реализации).

## Соответствие HTTP-методов доменным командам

| HTTP | Использование | Пример |
|---|---|---|
| `GET` | Запрос, без побочных эффектов | `GET /wallets/{id}` |
| `POST /{collection}` | Команда создания агрегата | `POST /operations` → `CreateOperationCommand` |
| `POST /{resource}/{action}` | Именованная доменная команда, не являющаяся CRUD (нет более подходящего HTTP-метода) | `POST /wallets/{id}/archive` → `ArchiveWalletCommand`, `POST /wallets/{id}/set-primary` → `SetPrimaryWalletCommand`, `POST /operations/{id}/restore` → `RestoreOperationCommand`, `POST /transfers/{id}/restore` → `RestoreTransferCommand` |
| `PATCH` | Частичное обновление изменяемых полей агрегата | `PATCH /operations/{id}` → `UpdateOperationCommand` |
| `PUT` | Полная замена одного конкретного поля с особым инвариантом | `PUT /wallets/{id}/currency` — выделено в отдельный эндпоинт, а не часть `PATCH`, так как имеет уникальное ограничение (запрет при наличии операций, включая мягко удаленные, Q15; новая валюта — только активная). `PUT /wallets/{id}/stated-balances/{date}` → `SetStatedBalanceCommand` — идемпотентная установка значения по естественному ключу (кошелек, дата): «повторный ввод заменяет» (ADR-0003 §6, п.8) |
| `DELETE` | Команда удаления. Для кошельков и элементов справочников — физическое удаление, может быть отклонено (`409`), если сущность имеет историю или используется. Для операций и переводов — **мягкое** удаление (запись остается, см. ниже) | `DELETE /operations/{id}` |

Отдельные `POST .../archive`, `.../set-primary`, `.../deactivate` (только для типов кошелька и типов операций — у валюты деактивации нет), `.../restore`, `.../refresh` — осознанное отступление от чистого REST («никаких глаголов в URI» из общих рекомендаций) в пользу явного соответствия доменным командам из `ddd-model.md` §6: это не CRUD-операции над атрибутом, а именованные бизнес-операции со своими инвариантами (например, `set-primary` атомарно снимает флаг с прежнего основного кошелька) — сворачивать их в `PATCH { isPrimary: true }` скрыло бы это от читателя контракта.

## Мягкое удаление и восстановление операций и переводов

Правила — [ADR-0002](../architecture/adr/0002-record-lifecycle.md), §3 и §5; сценарии UC-14, UC-16 в [user-scenarios.md](../requirements/user-scenarios.md).

- `DELETE /operations/{id}` и `DELETE /transfers/{id}` → `204`: мягкое удаление с **любой** датой, включая сегодняшнюю. Запись остается в БД; физического удаления операций и переводов нет. Перевод удаляется вместе с обеими «ногами».
- `POST /operations/{id}/restore` → `200` с восстановленной `Operation`; `POST /transfers/{id}/restore` → `200` с восстановленным `Transfer`. Перевод восстанавливается целиком.
- В `Operation` и `Transfer` — обязательные поля `isDeleted: boolean` и `deletedAt: date-time | null` (по образцу `Wallet.isArchived`). У «ног» перевода `deletedAt` совпадает с `deletedAt` перевода.
- `GET /operations`, `GET /transfers` и `GET` по `id` **всегда** возвращают мягко удаленные записи с `isDeleted = true`; параметра, скрывающего их, нет. Порядок и курсорная пагинация прежние.
- Удаленная запись исключена из расчетов: `GET /wallets/{id}/balance`, слепки, `GET /reporting/total-amount` (текущая и историческая). Удаление и восстановление запускают каскадный пересчет слепков (для перевода — обоих кошельков).
- `PATCH /operations/{id}` удаленной операции → `409` (сначала восстановить). Редактирование, удаление и восстановление «ноги» перевода через `/operations/{id}` → `409`: только через `/transfers/{id}`.
- Удаление и восстановление фиксируются в аудите (`GET /audit-entries`) действиями `Deleted` и `Restored`.

Связанные правила физического удаления (ADR-0002, §2, §4):

- `DELETE /wallets/{id}` → `204` для кошелька без операций; его слепки баланса и заявленные балансы (корректирующие суммы, `isCorrection = true`) удаляются вместе с ним (каждый — отдельной записью аудита: слепок — `SnapshotDeleted`, корректирующая сумма — `Operation`/`Deleted` с полным снимком). Заявленные и корректирующие суммы историей кошелька не считаются. `409` — есть операции (включая мягко удаленные; используйте `/archive`) либо кошелек основной.
- `PUT /wallets/{id}/currency` → `200` для кошелька без операций; слепки перестраиваются в новой валюте, корректирующие суммы заявленных балансов следуют за кошельком теми же числами (аудит `Updated`). `400` — валюта с таким `currencyId` не активна (не найдена среди активных). `409` — есть операции (включая мягко удаленные); заявленные балансы смену валюты не блокируют.
- `DELETE /operation-types/{id}` → `409`, если элемент используется кошельком или операцией (включая мягко удаленные; используйте деактивацию).
- `DELETE /currencies/{id}` — «убрать из активных» (у валюты нет деактивации, [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7) → `204`; `409`, если валюта используется кошельком или операцией (включая мягко удаленные). Курсы использованием валюты не считаются: при удалении валюты ее курсы (последние и исторические) и данные о покрытии истории удаляются вместе с ней. Валюта остается среди доступных.

## Заявленный баланс и корректирующая сумма

Правила — [ADR-0003](../architecture/adr/0003-balance-history.md), §6, [ADR-0002](../architecture/adr/0002-record-lifecycle.md), §2–§3; сценарий UC-24 в [user-scenarios.md](../requirements/user-scenarios.md).

- `PUT /wallets/{walletId}/stated-balances/{date}` с телом `{ amount }` (`operationId: setStatedBalance`, тег Operations; `amount` — строка-десятичное в валюте кошелька, отрицательная допустима) заявляет баланс кошелька на **конец дня** `date`. Ответ — корректирующая сумма как `Operation`: `isCorrection: true`, `statedBalance` = X (`Money`), `amount` — рассчитанная системой сумма со знаком (может быть нулевой), `operationTypeId: null`, `adjustmentMode: null`, `isDeleted: false`.
  - `201` — баланс на эту дату заявлен впервые; `200` — заменен (повторный ввод: запись та же, `id` не меняется); ввод того же значения — `200` без изменений (без аудита и без записи в `wallets`).
  - `400` — дата вне `[accountingStartDate .. сегодня]` либо сумма не число. `404` — кошелек не найден. `409` — запись изменена параллельно (повторите запрос).
  - В одной транзакции обновляются корректирующие суммы кошелька, его текущий баланс, слепки от даты заявления до сегодня и аудит.
- **Название** корректирующей суммы в ответе не передается: клиент выводит его по знаку `amount` — «Неизвестные траты» (меньше нуля) или «Неизвестные доходы» (больше нуля).
- `PATCH /operations/{id}`, `DELETE /operations/{id}` и `POST /operations/{id}/restore` корректирующей суммы → `409` («Это корректирующая сумма — её рассчитывает система…»; чтобы изменить сумму, добавьте недостающую операцию или исправьте существующую, чтобы заменить заявленный баланс — повторите `PUT` на ту же дату). Эта проверка выполняется **раньше** проверок «часть перевода» и «удалена».
- `GET /operations` включает корректирующие суммы, кроме **нулевых** (§6, п.7). Внутри одного дня корректирующая сумма идет после всех остальных операций этого дня (порядок `(operationDate, isCorrection, createdAt)` по возрастанию); курсорная пагинация без дублей и пропусков, прежние курсоры продолжают работать. Фильтр `operationTypeId` корректирующие суммы не включает (у них нет типа); `walletId`, `dateFrom`, `dateTo` применяются как к обычным операциям. `GET /operations/{id}` возвращает и нулевую корректирующую сумму.
- `POST /operations` и `PATCH /operations/{id}`: корректировка — только `adjustmentMode: Delta` (сумма изменения со знаком), работает как раньше. **`adjustmentMode: Absolute` → `400`** с текстом «Новое значение баланса задается действием „Указать баланс на дату“». Несовместимое изменение проводного формата относительно предыдущих версий (принятый риск preview-сборок): `operationTypeId` в `Operation` может быть `null`, добавлены `isCorrection` и `statedBalance`.
- Корректирующие суммы пересчитываются в той же транзакции при любом изменении операций кошелька (`POST`/`PATCH`/`DELETE`/`restore` операции, создание/удаление/восстановление перевода — по обоим кошелькам); `GET /wallets/{id}/balance` и `/balance-history` их включают: баланс на дату заявленного баланса равен `statedBalance`.
- Корректирующая сумма не подлежит мягкому удалению и историей кошелька не считается (см. «Связанные правила физического удаления»).

## Валюты: доступные и активные

Правила — [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §7–§9; сценарии UC-01, UC-02, UC-08, UC-09, UC-21, UC-28 в [user-scenarios.md](../requirements/user-scenarios.md).

- `GET /currencies/available` → `200`, **массив** `AvailableCurrency { code, name, isActive }` из БД, отсортированный по `code`. **Без пагинации** — осознанное исключение из единого курсорного формата (раздел «Пагинация»): список целиком нужен для выбора в комбобоксе (≈166 валют) и ограничен сервисом курсов. До первой загрузки списка — `[]`. К сервису курсов не обращается. `isActive` — валюта уже добавлена в активные. Названия английские, из сервиса.
- Список доступных обновляется вместе с курсами (старт приложения, суточный прогон, `POST /exchange-rates/refresh`), в том числе без основного кошелька. Пользователь им не управляет.
- `GET /currencies` — только **активные** валюты `Currency { id, code, name }` (поля `isActive` и параметра `includeInactive` нет).
- `POST /currencies` с телом `{ code }` → `201` с `Currency` (название берется из доступных); `400` — кода нет среди доступных (произвольный код, криптовалюта) либо ошибка валидации; `409` — валюта уже активна.
- `POST /currencies/{id}/deactivate` не существует (удален): состояния «деактивирована» у валюты нет.
- `POST /wallets` принимает валюту **кодом**: `currencyCode` (строка, до 16 символов) вместо `currencyId`. Код доступен, но не активен → валюта становится активной в той же транзакции (запись аудита `Currency`/`Created`), кошелек создан → `201`; код уже активен → используется существующая валюта; код ни активен, ни доступен → `400`, валюта не создается; создание кошелька отклонено проверкой (например, пустое название) → активация откатывается. Несовместимое изменение проводного формата относительно предыдущих версий (принятый риск preview-сборок).
- `PUT /wallets/{id}/currency` по-прежнему принимает `currencyId` и только **активную** валюту (`400` для неизвестного). Выведено при реализации из ADR-0004 §7.

## Курсы и общая сумма: чтение только из БД

Правила — [ADR-0004](../architecture/adr/0004-currencies-and-exchange-rates.md), §4–§6, §8, §9; сценарии UC-08…UC-10, UC-21.

- Ни один `GET` не обращается к сервису курсов: `GET /exchange-rates/latest`, `GET /currencies`, `GET /currencies/available`, `GET /reporting/total-amount` (текущая и историческая) читают только БД.
- `GET /reporting/total-amount?date=…`: курс на дату или ближайший более ранний (выходной); `ratesAsOfDate` — фактически примененная дата. Если подходящего курса нет (в том числе пока история курсов не догружена), кошелек **исключается** из суммы с указанием причины в `excludedWallets[].reason` (с кодом валюты и датой, например «Курс валюты EUR на дату 2026-05-01 недоступен.») — сумма неполная, ошибки нет.
- `POST /exchange-rates/refresh` обновляет курсы только **активных** валют и список доступных валют; историю курсов в запросе не догружает, но после ответа запускает ее дозагрузку в фоновом процессе. `502` — не удалось обновить пары либо список доступных: источник недоступен, ответ со списком пуст или неразборчив, список не удалось сохранить (возвращаются последние известные курсы). Кнопка доступна и без основного кошелька: в этом случае обновляется только список доступных.

## Пагинация

Единый курсорный формат для всех коллекций (`{ data: [...], pagination: { nextCursor, hasMore } }`) — даже для заведомо небольших списков (`wallet-types`, `currencies`), чтобы клиент Angular использовал один и тот же паттерн работы со списками везде. Курсор непрозрачен (opaque) — клиент не должен его парсить. Единственное исключение — `GET /currencies/available`: простой массив без пагинации (весь список сервиса нужен целиком для выбора, см. «Валюты: доступные и активные»).

## Ошибки

Формат — RFC 7807 Problem Details (`application/problem+json`) везде. Основные коды:

| Код | Когда |
|---|---|
| `400` | Некорректное тело запроса (не проходит валидацию схемы). Также: `adjustmentMode = Absolute` в `POST`/`PATCH /operations` (значение не поддерживается, новое значение баланса задается `PUT /wallets/{id}/stated-balances/{date}`); дата заявленного баланса вне `[accountingStartDate .. сегодня]` или сумма не число; код валюты недоступен (нет среди доступных и не активен) в `POST /currencies` и `POST /wallets`; неактивная валюта в `PUT /wallets/{id}/currency` |
| `401` | Отсутствует/недействителен `Bearer`-токен |
| `404` | Сущность с указанным Id не найдена |
| `409` | Нарушение доменного инварианта (список — в описании конкретных ответов `openapi.yaml`). Например: удалить кошелек, у которого есть операции (включая мягко удаленные), или основной кошелек; сменить валюту кошелька с операциями (включая удаленные); архивировать основной кошелек; перевод между разными валютами; удалить элемент справочника, используемый кошельком или операцией (включая удаленные), либо убрать из активных используемую валюту; добавить в активные уже активную валюту; удалить или восстановить «ногу» перевода через `/operations/{id}`; повторно удалить удаленную запись или восстановить не удаленную; редактировать удаленную операцию; редактировать, удалять или восстанавливать корректирующую сумму заявленного баланса (системная запись); параллельное изменение записи, в том числе гонка двух заявлений баланса на одну дату |
| `429` | Только на `/auth/login` — превышен лимит попыток |
| `502` | Только `/exchange-rates/refresh` — Frankfurter недоступен либо не удалось обновить курсы пар или список доступных валют (при этом возвращается 200 с последним известным курсом для планового автообновления; 502 — только когда пользователь явно запросил обновление и хочет знать, что оно не удалось) |

Rate limiting за пределами `/auth/login` не предусмотрен — однопользовательское приложение без публичного мультитенантного API, ограничивать по нагрузке нечего; это осознанное отступление от чек-листа skill'а `api-designer` («не забывай про rate limiting»), а не упущение.

## Версионирование

Префикс пути `/api/v1`. Следующая версия (если понадобится breaking change) — `/api/v2`, со временным сосуществованием обеих, пока Angular-клиент не перейдет на новую — детальная политика deprecation избыточна для внутреннего API с одним-единственным клиентом (собственный Angular SPA), но префикс версии заложен заранее, чтобы не переделывать все пути задним числом.
